## Existing behavior and boundaries

Passwords remain 15–128 Unicode code points and at most 512 UTF-8 bytes, without trimming/normalization. Names remain the only fields accepted by the current profile PATCH. Sources inform the controls; exact lifetimes, limits and workflows below are project decisions. OWASP recommends current-password checks for sensitive changes and, without MFA, confirmation through both addresses for an email change. We select that stronger mailbox requirement. ## Chosen user and session policies

| Operation | Required proof and effect |
|---|---|
| Password change | Active authenticated session plus current password; replacement must differ from the current password. Update password, increment credential version, invalidate outstanding security tokens/pending email change and revoke **all** sessions, including the caller, in one transaction. Require a fresh login; do not issue replacement credentials. |
| Verify current email | Active session plus current password at issuance and confirmation, and the emailed verification token bound to that account/current email. Mark verified only on confirmation. Do not change password, revoke sessions or automatically log anyone in. |
| Change email | Current address must already be verified. Require active session/current password at initiation and each confirmation. Require distinct proofs sent to both current and proposed addresses. Keep the current login/recovery address until the second proof commits. Then atomically replace email, retain verified status with a fresh verification timestamp, increment credential version, invalidate other tokens/pending requests and revoke all sessions. Fresh login uses the new email. |
| Forgotten-password reset | Token for an active account's current verified email plus a valid replacement password; no session/current password is required. Atomically change password, increment credential version, consume/invalidate all security tokens, cancel pending email change and revoke all sessions. No automatic login. |

All new and existing users start with unverified email after the verification migration; never backfill verified status from account age, signup or prior login. Keep signup's deliberate login and existing customer/admin capabilities unchanged, including checkout: verification is not a new shopping authorization rule. After login, show an account-security reminder and a deliberate current-password-protected verification action. Registration itself sends no email. This avoids an unauthenticated signup mail trigger and gives legacy accounts the same enrollment path as new accounts.

Recovery and email changes require verified email. Users who forget their password before enrollment, or lose the current mailbox needed for a dual-confirmation email change, have no self-service bypass in this project. Explain that limit without inventing a support endpoint, administrator password-reset shortcut or automatic verification. Existing accounts with a known password can enroll without data loss. Administrative fixture accounts follow the same rule; role/activity controls remain operator-only.

Wrong current password is **403 `reauthentication_failed`**, not 401. A 401 means bearer/session authentication failed. Password/email/reset changes revoke database sessions, so already-issued JWTs fail subsequent authentication; already-authorized requests cannot be recalled. Security mutations must recheck the caller's session under the transaction locks to reject requests authorized before a concurrent revocation. No new JWT claims, token blacklist or signing-key rotation is needed.

## Tokens and pending email state

Use 32 random bytes from `crypto/rand`, raw base64url encoded (43 characters). Store only SHA-256 digests, with unique digest constraints; raw secrets exist only in request/mail memory and the user's mailbox. Tokens are opaque, purpose-bound, account-bound and tied to the current email and `credential_version`. They are not JWTs, passwords, sessions or login credentials.

| Purpose | Validity | Issuance/reuse rule |
|---|---|---|
| `verify_email` | 30 minutes | One current verification token per user. A deliberate resend invalidates its predecessor. |
| `email_change_old`, `email_change_new` | 30 minutes from request creation | Two independent tokens on one pending request, one proof per mailbox. Replacing the pending request invalidates both old tokens; no expiry extension on proof submission. |
| `reset_password` | 15 minutes | Up to three live tokens per user. Another unauthenticated request does not invalidate earlier links. Successful reset invalidates all of them. |

At redemption require exact token syntax, expected purpose/account, active user, matching credential version/email, unexpired database time and no consumed/invalidated timestamp. Email-change proofs additionally require the current matching pending request and its expected old/new address. Check expiry using `clock_timestamp()` after waiting for locks. Reject wrong-purpose, missing, expired, consumed, cancelled and foreign-account links with the same **400 `invalid_security_token`**. Never disclose which token/account predicate failed. A used token cannot repeat a successful mutation; transport uncertainty is resolved by deliberate login/status reads, not token replay.

Proof consumption and its state change occur in the same transaction. First email proof records one confirmation and returns pending; the second updates the user and completes the request atomically. Neither GET navigation nor mail-link preview consumes a token. A rollback consumes nothing. Definitive duplicate-email conflict at final confirmation terminates the pending request and invalidates its remaining proofs without changing the user's address; return 409 `email_conflict`. For this explicit conflict outcome, commit that cancellation before responding. Never treat an unknown COMMIT result as a proven rollback.

Use a pgx savepoint around the final email UPDATE: after the expected `users_email_key` uniqueness violation, roll back that savepoint before recording/committing request cancellation. Catching a uniqueness error in an already-aborted outer PostgreSQL transaction is insufficient. A failed/uncertain outer COMMIT returns `security_outcome_unknown`, not a falsely definitive conflict. Other unexpected constraints fail closed without being mislabeled as duplicate email.

Retain invalid/consumed/expired rows for seven days beyond expiry for bounded abuse counts and troubleshooting, without raw tokens or full-message storage. Task 4 adds a bounded, explicit operator SQL maintenance recipe using migration credentials (delete tokens before requests in separate committed batches of 500, never holding token locks while acquiring request locks); runtime has no DELETE grant. No background purge worker is added. Expired pending requests are marked expired under the user lock before replacement, so partial uniqueness is not dependent on a volatile time predicate.

These choices apply OWASP's non-disclosing requests, random expiring single-use recovery secrets, protected storage and normal login after recovery. Multiple valid reset links avoid letting a stranger invalidate the owner's link through repeated requests. [Password-recovery guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)

## Transaction ordering and schema plan

Every flow discovers IDs without locks, then locks **user → pending email request → security tokens → sessions** as applicable; order multiple rows of a type by UUID. Re-read all eligibility/state under locks. Argon2 verification/hashing happens before opening the transaction against a bounded snapshot; under the user lock compare both password hash and credential version, then recheck the caller session/activity. A changed snapshot returns **409 `credentials_changed`** for authenticated writes without applying them. For reset, a changed credential version makes the token invalid. Rehashing does not increment credential version; actual password/email changes do. Guard version increments against bigint exhaustion with 409 `credential_version_exhausted`.

**Task 3 refactor implemented:** [refresh](../../backend/internal/auth/service.go) now locates ownership without locking, locks the user first, then locks/revalidates the session verifier/revocation/expiry. Login's locked snapshot check includes password hash, credential version and canonical email. Password change locks the user and its sessions in UUID order before checking the caller's validated internal session ID; no body-supplied account/session ID is accepted. Logout still takes only session locks. PostgreSQL race/rollback/commit-loss evidence is linked above; future token/email flows must retain this order.

## Selected HTTP and browser contracts

Paths below are under `/api/v1`. Tasks 3–6 are implemented in OpenAPI 1.5.0, including both public reset operations. All bodies are strict JSON objects: required fields only, unknown/null/duplicate keys rejected, existing 64-KiB ceiling, no credentials/tokens in query strings. Oversized bodies return 413 `body_too_large`. Email input reuses existing normalization/validation; do not change identity matching, strip provider dots/tags or silently add Unicode transformations. Unicode recipient addresses require SMTPUTF8 support or delivery fails safely; no transliteration to another identity.

All new POSTs require exact configured Origin plus `X-CSRF-Protection: 1`, including public token/reset operations. GET security uses bearer auth without cookies; all authenticated security POSTs use bearer auth and `credentials: include` so confirmed session-ending responses can clear the existing refresh cookie. They authenticate by bearer/session, not by cookie. Public reset POSTs use `credentials: omit` and never read/set/clear another account's cookie. Separate CSRF policy from cookie policy in transport metadata; the existing coupling is insufficient for these public POSTs. Preserve current CORS allowlists/no-store headers.

|---|---|---|
| 3 | `POST /users/me/password` — `current_password`, `new_password` | 200 `SecurityChangeResult`; clear refresh cookie after confirmed commit. |
| 4 | `GET /users/me/security` | 200 `{email_delivery_available: boolean, pending_email_change: null or PendingEmailChange}`. Only the current owner sees ID/new address/expiry/proof flags. Treat expired/terminal requests as null. |
| 4 | `POST /users/me/email-verification` — `current_password` | 202 `MailRequestResult`; verified accounts return `not_required`. |
| 4 | `POST /users/me/email-verification/confirm` — `token`, `current_password` | 200 updated User; no session issuance/revocation. |
| 5 | `POST /users/me/email-change` — `new_email`, `current_password` | 202 `MailRequestResult`; inspect owned pending status through GET. Repeating intentionally replaces the prior request. |
| 5 | `POST /users/me/email-change/confirm` — `token`, `current_password` | 202 `{status: "pending"}` after first proof; 200 `SecurityChangeResult` after final change, clearing the refresh cookie. |
| 5 | `POST /users/me/email-change/cancel` — `request_id`, `current_password` | 204; cancel the matching pending request and invalidate its proofs. Missing/foreign ID is 404; no effect on a newer request. |
| 6 | `POST /auth/password-resets` — `email` | 202 `{message: "If this address is eligible, recovery instructions will be sent."}` for valid input regardless of existence/activity/verification/throttle/delivery result. |
| 6 | `POST /auth/password-resets/confirm` — `token`, `new_password` | 200 `SecurityChangeResult`; no cookie operation or automatic login. |

`MailRequestResult` is `{delivery: "accepted"|"unconfirmed"|"not_required"}`; accepted means SMTP accepted the message(s), not inbox receipt. Authenticated sender errors after committed issuance return unconfirmed, retaining pending state. `SecurityChangeResult` is `{reauthentication_required: true, notification: "accepted"|"unconfirmed"|"not_applicable"}`; it confirms the credential transaction, independently of its post-commit notification. Notification failure never rolls back a committed password/email change. `PendingEmailChange` has UUID `id`, canonical `new_email`, date-time `expires_at`, and boolean `old_confirmed`/`new_confirmed`; no proofs or token strings.

Common failures: 400 `invalid_json` or generic `invalid_security_token`; 401 `unauthorized` only for missing/revoked/expired session; 403 `csrf_rejected`/`origin_rejected`/`reauthentication_failed`; 409 `credentials_changed`, `credential_version_exhausted`, `email_conflict` or `email_verification_required`; 422 `invalid_input` (including same current/replacement password or unchanged email); 429 `rate_limited`/`auth_capacity` with Retry-After; 503 `security_unavailable` for precommit service/capacity/configuration failure and `security_outcome_unknown` when commit cannot be confirmed. Public request outages are handled separately below. Keep known input failures distinct from uncertain mutation results; never expose raw SQL/SMTP errors.

## Delivery configuration, failure and abuse budgets

Select provider-neutral **SMTP submission**, using installed Go's `net/smtp` client plus `net.Dialer`/`crypto/tls`. This package is frozen but contains the small SMTP/STARTTLS/AUTH operations needed here; no new module is justified. Use `smtp.NewClient` over a context-bound connection, not unbounded `smtp.SendMail`. Require STARTTLS with hostname/certificate validation and TLS 1.2 minimum, then AUTH PLAIN; do not downgrade, skip verification or authenticate before TLS. Support a verified implicit-TLS connection as the second explicit mode. [Go SMTP reference](https://pkg.go.dev/net/smtp)

| Planned environment setting | Validation / default |
|---|---|
| `MAIL_MODE` | `disabled` by default in local; `smtp` required in production from task 4. Disabled email-dependent operations fail 503 before issuance; public requests use that same result for every address. Password changes still work. |
| `SMTP_HOST`, `SMTP_PORT` | Required explicit hostname and port 1–65535 in smtp mode; no URL credentials/path. No assumed server/port/provider. |
| `SMTP_TLS_MODE` | Explicit `starttls` or `tls`; no cleartext network mode. |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | Both required and nonempty in smtp mode; private server configuration only. Never log or export through Vite. |
| `MAIL_FROM` | Explicit single ASCII mailbox controlled by the operator; no display name, CR/LF or arbitrary caller-provided From/Reply-To. |

Build links from existing validated `FRONTEND_ORIGIN` and fixed route paths, never Host/Forwarded headers or a return URL. Production uses HTTPS; loopback HTTP stays a local exception. Plain-text UTF-8 MIME bodies, fixed ASCII subjects, standard address/header encoders and CR/LF rejection prevent header injection. No attachments, remote images, click tracking or password/profile payloads. Non-ASCII envelope addresses require SMTPUTF8 capability. Operators supply a permitted sender and submission credentials; SPF/DKIM/DMARC and actual inbox deliverability are provider/domain configuration, not application features or assumed successes.

Send synchronously **after confirmed DB commit**, with no transaction lock held during SMTP and no automatic retry. Use one two-second overall SMTP budget (including dial/TLS/AUTH and up to two messages), two concurrent send batches per process, bounded message size 16 KiB and immediate capacity refusal. Close connections on context cancellation and deadline. Authenticated handlers retain their current five-second upper bound; use the remaining request budget for post-commit mail. If that is exhausted, report notification/delivery unconfirmed. These strict lab budgets may reject a slow real relay; record actual test results rather than silently increasing request/lock budgets.

There is no transaction spanning PostgreSQL and SMTP. A crash after issuance commit may lose delivery; users can deliberately resend/restart the request. A lost SMTP acknowledgment may still deliver; issued tokens remain valid until normal use/expiry/invalidation. Never send a token after an unconfirmed issuance commit. Recheck email/version/token validity immediately before sending; an unavoidable subsequent race may deliver a stale link, which must fail redemption. Notifications are best-effort post-commit messages; there is no durable/exactly-once notification guarantee. If durable notification is later required, that is a separate approved scope change, not a hidden outbox.

Password change/reset notifications go only to the current verified email; email-change initiation sends the two confirmation messages, and completion sends notifications to both old/new addresses. Do not send security notifications to an unverified address. Task 3 exposes `not_applicable` until verification/delivery is implemented; task 4 wires password-change notifications and includes their regression tests before delivery-dependent acceptance. In final M9, disabled/unavailable delivery means unconfirmed for a committed credential change, never a false claim that mail was sent.

Uniform scheduling reduces timing enumeration; it is not a constant-time network guarantee. Test known/unknown/inactive/unverified/rate-suppressed and SMTP failure paths under the same deterministic clock/budget, plus real timing bounds without asserting identical network durations. Malformed input/CSRF/IP/global-limit/disabled-service responses may differ because those checks do not depend on account existence. Delivery failures are logged only as safe category/request ID, never recipient, token, credentials or message content.

## Browser/session integration and link safety

Add `/account/security` for password change, verification reminder/actions and owned pending-email controls. Mail links use `/verify-email#token=...`, `/confirm-email-change#token=...` and `/reset-password#token=...`; `/forgot-password` holds the request form. These are dedicated minimal layouts without catalog images or external requests. Add `Referrer-Policy: no-referrer`/HTML metadata before rendering them; fragment tokens also stay out of HTTP request targets. [Referrer-policy behavior](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Referrer-Policy)

Capture/validate the single fragment token once at application bootstrap before routing/auth restoration, immediately remove it with `history.replaceState`, and retain it only in volatile, tab-local memory. Do not put it in router state, returnTo, storage, analytics, console, broadcast messages or diagnostics. Invalid/repeated/oversized fragment fields show a generic invalid-link screen. A reload discards the token; instruct the user to reopen the original email. A mail scanner opening a GET cannot confirm/reset anything: the user must submit a form. Password confirmation is a UI-only second input; compare it before sending the single new-password field and clear both after each request.

Verification/email-change confirmation pages keep the token in that volatile page context while offering inline sign-in if needed; do not redirect through an auth URL carrying the token. Confirmation requires the intended account's active session/current password; a different account receives the generic invalid-token response. Explicitly switching identity discards retained intent; the user can reopen the email. No token can turn into a general session or bypass the two mailbox proofs.

Implement a dedicated session-controller path for security writes: acquire the existing same-origin Web Lock, pin identity/revision and **send once**. It may renew/check identity before the explicit write, but does not use the generic definitive-401 mutation replay. Keep private state hidden after a potentially session-ending uncertain outcome, discard password inputs and require deliberate normal login/checking the new credential. Never automatically repeat a password/email/reset write or generate a replacement intent after timeout.

After confirmed authenticated password/email change, the server clears the existing cookie (`/api/v1/auth`, same security attributes); the controller clears private state and broadcasts only the existing signed-out notice. No bearer token/profile/password enters the channel. For public reset, omit cookies and do not revoke/clear an unrelated currently signed-in account: after success send a small new `security-changed` notice, hide private state and perform one coordinated cookie/profile recheck in all same-origin tabs. A matching account's revoked session becomes signed out; an unrelated valid account can restore. This is an observation, not automatic login as the reset target. Keep the revoked cookie harmless until normal login replaces it or explicit logout clears it. Other devices learn revocation on their next server check; no push service is added.
