## 3. Initialization and migrations

Initialize the complete approved 13-table schema before exposing checkout. Use five sequential goose migration groups: identity; catalog/inventory; carts/items; orders/items/reservations; payments/idempotency/history. Add indexes alongside their owning tables, including the partial unique active-attempt index. Goose's metadata table is additional to the 13 domain tables.

Use the physical DDL without introducing unknown-payment states, expiring checkout keys, billing-address types, or a second payment idempotency column. Keep the existing explicit indexes initially; index removal requires a separate justified change. UUIDv4 identifiers are generated in Go, without a PostgreSQL UUID extension.

Migration 6 adds column-scoped authentication grants to the runtime role: customer/cart creation, session insertion/rotation/revocation, and password rehash updates. It adds no tables and does not permit role/activation changes or writes to goose metadata. The five initial schema groups remain unchanged.

Migration 7 adds the column writes required for profiles, saved addresses, products, on-hand inventory, and cart items/versions. At that stage reservation-counter writes remain denied. Migration 8 adds reserved-counter updates and column-scoped insertion of the complete T1 order/items/reservations/payment/history/idempotency graph. Migration 9 adds order/reservation status and timestamp updates, plus payment status/start/completion/failure-code updates. Runtime SQL still cannot change user roles/activation, reassign ownership, physically delete products, change goose metadata, rewrite snapshots or attempt scenarios/identities, or update/delete history and idempotency records. These grants do not distinguish customer/admin requests: the trusted application enforces principal ownership and current-role checks before invoking the services. PostgreSQL credentials must remain server-side.

Goose migrations are the sqlc schema source. Put `sqlc.yaml` at the root, SQL queries under `backend/internal/db/queries`, and generated pgx/v5 code under `backend/internal/db/sqlc`. Use native pgx UUID and nullable types, `int64` for cents/version, `int32` for SQL integers, and explicit API mapping. Validate the JSONB shipping snapshot through a typed service structure.

Migration execution is an explicit one-shot operation, not API startup behavior. Runtime credentials have only required data access; migration credentials own schema changes. Down/reapply checks are limited to disposable databases. Development fixtures are explicit, separate from schema migrations, and never create a default administrator.

**Reason:** T1 must create payment/history records from its first usable implementation. One schema source and visible transaction boundaries reduce drift and hidden behavior.

## 4. Compose, configuration, and startup

Use root `compose.yaml` for PostgreSQL only, beside the ignored root `.env`, with a named volume and a configurable loopback-only host port (default 5432). On 2026-10-19 the Compose file moved from `infrastructure/` to the root so ordinary `docker compose` commands discover the configuration and environment together. Keep `infrastructure/postgres/init.sh` as the bootstrap source, mounted read-only from `./infrastructure/postgres/init.sh`. Preserve project name `ecom` and volume key `postgres_data`, resolving to the existing `ecom_postgres_data` volume. Development scripts explicitly select the root Compose/env files. The API runs locally at `127.0.0.1:8080`; it connects through the database's loopback port. Containerized API deployment is deferred.

Use the local binaries through [PowerShell](../../scripts/dev.ps1) or [Bash](../../scripts/dev.sh); do not add Docker tooling/test profiles. No destructive volume reset runs as part of ordinary startup. Bootstrap establishes restricted runtime access; migrations 6–9 supply the implemented column-scoped writes described above. The runtime role cannot change goose metadata. Initialization runs only on a new database volume: editing `.env` does not rotate existing PostgreSQL passwords.

Provide `.env.example` without working secrets; ignore the real local env file. Require database URLs and a random JWT secret explicitly. Refuse missing/invalid secrets and unsupported environment modes. Database credentials use SCRAM authentication; local isolated Compose connections may explicitly disable TLS, while nonlocal connections must verify TLS. Do not log connection strings or token material.

Current code defaults: pgx pool maximum 10/minimum 0 connections; connect timeout 5 seconds; request/service work bounded by a 5-second context; PostgreSQL session defaults `lock_timeout=2000` and `statement_timeout=5000` milliseconds. HTTP read-header timeout 5 seconds, read timeout 10 seconds, write timeout 15 seconds, idle timeout 60 seconds, graceful shutdown budget 10 seconds, and JSON body limit 64 KiB. These budgets are code settings, not supported environment-variable overrides. Checkout shares its operation deadline across phases; commit resolution and rollback cleanup have separately bounded budgets as described below.

The [API entry point](../../backend/cmd/api/main.go) composes services/handlers and runs the HTTP listener in a goroutine so the main execution can wait for either listener failure or a shutdown signal. Shutdown stops accepting requests and allows in-flight work up to ten seconds. This lifecycle concurrency does not create asynchronous payment processing. The [configuration loader](../../backend/internal/platform/config/config.go) reads process settings; development scripts load the ignored `.env` and construct database URLs. Neither binary loads that file or runs migrations itself.

Expose `/health/live` and `/health/ready` at the root. Liveness checks process responsiveness; readiness performs a bounded database ping and checks goose schema version 11. The API can listen while unready; readiness does not apply migrations, audit every runtime grant or scan data integrity. Recovery checks readiness before inspecting candidates. Expose root `/metrics` only to authenticated active administrators, with an in-process authenticated-request counter in Prometheus exposition text; no collector is installed. Use structured standard-library logging and request IDs. Exclude passwords, bearer/refresh tokens, cookies, and shipping-address contents from logs and metric labels.

`APP_ENV=production` validates an HTTPS frontend origin and verified PostgreSQL TLS, and enables Secure cookies. It does not install certificates, enable HTTP-server TLS or serve frontend assets: the current listener uses `ListenAndServe`. Planned application/SPA packaging, HTTPS delivery and immutable release identification belong to [Milestone 14](../IMPLEMENTATION_SEQUENCE.md#final-release-gates--milestone-14). No deployment mechanism or new infrastructure is introduced by this review.

**Reason:** Explicit startup and resource bounds make failure understandable. Separate runtime and migration privileges limit accidental schema changes.

**Tradeoff:** Each process has its own bounded pool, limiter state and counters. The current local deployment is not a horizontally scaled or production-verified environment; production mode alone is not deployment evidence.

## 5. Passwords

M9 task 5 reuses schema 11 and the same user → pending request → token → session lock order for email changes. It issues independent proofs to both mailboxes, keeps the old email until the second proof, and preserves the user ID when changing verified email/version and revoking all sessions. A savepoint isolates only the expected `users_email_key` violation so a final duplicate conflict can commit request termination in a usable outer transaction; unknown COMMIT never becomes a definitive conflict. Cancellation pins the exact request ID and cannot affect a newer request. The existing indexed old-mailbox token issuance row counts each request once for the persistent mail budget, including cancellation and failed delivery; no extra index/migration is required. SMTP remains bounded, post-commit and best effort. [Security design](ACCOUNT_SECURITY_DESIGN.md) and [operations](OPERATIONS.md#security-email-configuration-and-verification) own the shared policy and workflow.

M9 task 4 adds standard-library TLS SMTP and explicit email verification under the [security design](ACCOUNT_SECURITY_DESIGN.md). Only SHA-256 token digests and immutable account/email/version bindings persist; active-session/current-password checks and ordered row locks guard issuance/consumption. Database-clock expiry and persisted issuance counts survive process restarts. Mail runs once after known commit, within its two-second/two-batch budget; ambiguity is `unconfirmed` and never undoes credentials or triggers a retry. Existing emails remain unverified until mailbox proof. Verified password changes notify best effort; verification preserves sessions. Migration 11 supplies shared token/request storage, readiness 11 and scoped grants without a queue/outbox/service dependency. [Operations](OPERATIONS.md#security-email-configuration-and-verification) and [evidence](../frontend/TEST_PLAN.md#milestone-9-email-verification-progress) own configuration/receipt/pruning and acceptance.

M9 task 3 implements current-password-verified replacement, credential versioning and all-session revocation under the [account-security design](ACCOUNT_SECURITY_DESIGN.md). Login and refresh lock the user before session work; login rechecks password hash/version/email and security writes recheck the caller session under locks. The transaction increments the internal version and revokes sessions together, reporting uncertain COMMIT as 503 without retry. Notification is currently `not_applicable`; email/verification/token tables remain task 4 onward. Existing hashing parameters below are unchanged.

Use Argon2id through `golang.org/x/crypto/argon2`: 64 MiB memory, 3 iterations, parallelism 1, a cryptographically random 16-byte per-password salt, and a 32-byte derived key. Store a PHC-format string containing algorithm/version/parameters/salt/hash. Use constant-time derived-key comparison, strict encoded-hash parsing with allocation bounds, and rehash weaker accepted verifiers after successful login. The [password implementation](../../backend/internal/auth/password.go) and [benchmark](../../backend/internal/auth/password_test.go) support verification; historical measurements belong in [authentication evidence](evidence/MILESTONE_1_AUTHENTICATION.md), not an assumed performance guarantee. Parameter changes require an explicit policy decision.

Accept 15–128 Unicode code points and at most 512 UTF-8 bytes. Do not trim, normalize, truncate, or impose character-class rules on passwords. Return generic login failures and perform a policy-matched dummy verification for nonexistent accounts. Bound concurrent Argon2 work to 2 operations per API process; reject excess authentication work with 429 rather than permitting unbounded allocations. Bound the inputs before hashing.

**Reason:** Argon2id provides adjustable memory-hard password verification; the encoded parameters allow upgrades. The limits support passphrases while bounding resource use. The 15-character minimum is a deliberate strengthening of the original 12-character contract for this password-only application.

**Tradeoff:** Hashing consumes substantial memory/CPU and the two-slot bound can return 429 under load. An Argon2 invocation checks cancellation before/after computation; it cannot be interrupted midway by the request context.

Sources: [OWASP password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [OWASP authentication guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), and [Go Argon2 package](https://pkg.go.dev/golang.org/x/crypto/argon2). The precise 64 MiB/3-iteration budget and concurrency limit are project choices, not measured performance claims.

## 6. JWT access tokens and authorization

Use `github.com/golang-jwt/jwt/v5` and HS256 with a dedicated cryptographically random secret of at least 32 decoded bytes, supplied as base64 configuration. Allow only HS256; reject unsigned tokens and algorithm substitution. No custom JWT implementation or external identity provider.

Access tokens expire after 15 minutes. Require signature validation, `typ=JWT`, issuer `ecom`, audience `ecom-api`, UUID `sub` (user), UUID `sid` (session), UUID `jti`, and `iat`, `nbf`, `exp`. Permit at most 30 seconds of clock skew; reject malformed claims, future issuance beyond skew, and a claimed lifetime greater than 15 minutes. Do not accept token-supplied key URLs or select secrets from untrusted headers.

For every authenticated request, verify the referenced session is unrevoked/unexpired and owned by the subject, and load the current active user and role. Deactivation, logout, and role changes affect subsequent authorization checks; already-authorized in-flight work is not forcibly cancelled. JWT role claims are not authoritative. Send access tokens only in the Authorization bearer header. The planned frontend holds them in memory, never localStorage/sessionStorage, and uses refresh after a reload.

**Reason:** HS256 is appropriate for one application that both issues and validates tokens. Database session checks use an already approved table and provide prompt revocation without a blacklist or cache. Short lifetimes bound exposure, while strict issuer/audience/algorithm checks prevent token confusion.

**Tradeoff:** Protected requests depend on PostgreSQL availability and add a session/user lookup. The dedicated signing secret is shared by this application's issuer/verifier; multi-service token trust and automated key rotation are outside the implemented baseline.

Implementation: [token validation](../../backend/internal/auth/token.go) and [current-session queries](../../backend/internal/db/queries/auth.sql).

Sources: [JWT best current practices, RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html) and [golang-jwt parser validation options](https://golang-jwt.github.io/jwt/usage/parse/). Lifetimes and the session-check policy are project decisions.

## 7. Refresh sessions, cookies, and abuse controls

Use opaque refresh tokens containing 32 random bytes encoded with base64url. Store only their SHA-256 digest in `user_sessions.refresh_token_hash`; a fast digest is appropriate for these high-entropy random secrets, unlike passwords. Set an absolute session expiry of 7 days, without sliding extension.

Creation and expiry use the same PostgreSQL transaction timestamp (`created_at` and `now() + interval '7 days'`), rather than comparing an application-clock deadline with a database-clock creation time. Rotation rechecks expiry against `clock_timestamp()` in the guarded update, after acquiring locks. Hash the exact canonical base64url cookie value as UTF-8. Token responses and cookies are emitted only after an acknowledged transaction commit. If a rotation commits but the response is lost, the old verifier cannot recover its replacement: require login again without claiming replay-family recovery.

Rotate the verifier atomically under the session row lock, updating `last_used_at`; exactly one concurrent refresh may succeed. A stale/replayed verifier returns 401. The frontend must serialize refresh calls, and a failed refresh must not clear a cookie written by a concurrent successful refresh. The existing schema does not retain old verifiers, so do not claim replay-family detection or revoke unrelated sessions on an unrecognized token. Transaction failure must not emit a replacement cookie.

Use a host-only `ecom_refresh` cookie, `HttpOnly`, `SameSite=Strict`, `Path=/api/v1/auth`, with `Secure` enabled by `APP_ENV=production`. Local mode omits Secure and is intended only for isolated loopback development; setting an HTTPS origin in local mode does not turn Secure on. Set its absolute Expires to the database deadline, truncated to whole seconds, without computing a positive Max-Age across application/database clocks. Logout uses Max-Age=-1 and a past Expires. Login/refresh token responses use `Cache-Control: no-store`.

Require an exact allowlisted Origin and `X-CSRF-Protection: 1` on login, refresh, and logout; login also requires JSON. Use the browser's frontend origin as the allowlist, initially `http://localhost:5173` in local mode; production requires an explicit HTTPS origin. Reject missing, `null`, and disallowed origins on those browser-cookie operations. CORS credentials are allowed only for exact origins, never `*`; allow the explicitly needed headers/methods and handle preflight without authentication. CLI/test clients must supply the same Origin/header values.

Logout uses the refresh cookie and does not require an unexpired access token. It revokes the matched session and clears the cookie with matching attributes; an absent/already invalid cookie still produces 204 after CSRF checks. Cookie-backed refresh requires a valid cookie and returns 401 otherwise.

Limit login/register to 20 requests per minute per peer IP and 5 per minute per canonical email using bounded, expiring in-process counters; cap each limiter map at 10,000 keys and fail closed with 429 when saturated. Trust no forwarded IP headers in this direct local deployment. No permanent account lockout or distributed limiter is introduced. Multiple processes would have independent limits and require a separate deployment decision. Saturation and rate limits include `Retry-After`.

**Reason:** Rotation and atomic verification limit token reuse. Origin/custom-header checks supplement cookie isolation; local CORS is explicit. Resource limits protect expensive hashing while preserving the approved single-application architecture.

**Tradeoff:** A lost refresh-rotation response can require signing in again. The browser must coordinate refresh and use compatible site/host settings for SameSite cookies; CORS permission alone does not make cross-site cookies work. Browser-origin/host setup and coordination are owned by [frontend integration](../frontend/API_INTEGRATION.md), with real browser verification still outstanding.

Source: [OWASP CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

Implementation: [cookie/session handlers](../../backend/internal/auth/http.go), [origin and authorization middleware](../../backend/internal/auth/middleware.go), and [bounded limiters](../../backend/internal/auth/limiter.go).

## 8. Accounts and administrator provisioning

Registration creates a customer and its persistent cart in one transaction. Email is trimmed/lowercased under the lab's existing policy. User endpoints cannot set roles or active flags. Duplicate canonical email returns the documented 409; login otherwise avoids account-existence disclosure.

Promote an explicitly selected, already registered active customer through the [parameterized operator procedure](OPERATIONS.md#provision-an-administrator), inspecting identity before the guarded update and verifying role afterward. Runtime credentials cannot perform it. No public promotion route, seeded admin password, or automatic first-user promotion. Physical account deletion is not exposed. Saved addresses are shipping addresses; no billing type is added.

**Reason:** The first administrator needs an intentional operator action, without expanding the HTTP surface or weakening public registration.

## 9. API schemas, input, and pagination

Keep OpenAPI 3.0.3. Define complete `Address` and `Product` responses separately from strict inputs; do not extend `additionalProperties: false` inputs with `allOf`. Root operational paths override the API's `/api/v1` server URL.

Reject unknown request fields, malformed JSON/UUIDs, nonintegral integer values, oversized bodies, and invalid headers. Use 400 for malformed structure/types, 422 for validly shaped but invalid values/business input, 401 for absent/invalid authentication, 403 for authenticated role denial or failed CSRF checks, 404 for missing/not-owned resources, 409 for state/uniqueness conflicts, 413 for oversized bodies, 429 for throttling, and 500 for unexpected failures. Return the existing `{code, message}` error shape without SQL details. Document operation-specific errors in OpenAPI, including 503 commit uncertainty for checkout. Framework-level errors must also use the error shape where an HTTP response can be written.

PATCH uses omitted fields as unchanged; JSON null is rejected. Empty PATCH returns 422. Empty strings clear optional textual fields (`label`, `line_2`, product description/image URL); map cleared optional text to SQL NULL and serialize it as an empty string. Required text is trimmed, nonblank, and length-bounded; passwords are exempt from trimming. Require country `US` (default when omitted), normalize US region codes to uppercase, and validate state/DC codes and ZIP/ZIP+4. Product images are optional HTTP(S) URLs up to 2,048 characters; do not fetch them on the server. SKU is trimmed, case-sensitive, 1–64 ASCII letters/digits/dot/underscore/hyphen. Names are at most 200 code points, address lines 200, city 100, labels 80, descriptions 4,000, and email 254.

Use `limit` 1–100 (default 20) and `offset` >=0 for product and order lists, retaining array responses. Products sort by name then ID; orders sort by creation time descending then ID descending. Payment history sorts by attempt number. Address lists sort by creation time then ID. Offset pagination can shift under concurrent writes; this is an accepted lab tradeoff.

For the implemented catalog, reject unknown/repeated pagination parameters and malformed decimal integers with 400; out-of-range values, including offsets beyond PostgreSQL BIGINT, return 422. Duplicate case-sensitive SKUs return 409 `sku_conflict` on creation or update. Profile/address/product PATCH queries apply supplied fields atomically instead of reading and rewriting omitted values. This prevents concurrent edits to different fields from overwriting one another.

**Reason:** Separate input/output contracts remain strict and valid. Explicit edge cases eliminate handler-specific interpretations without adding an API framework.

## 10. Numeric bounds and cart semantics

Use integer JSON numbers. Cap each unit price, line total, subtotal, and order total at 1,000,000,000,000 cents; validate checked multiplication/summation before any SQL money expression. These conservative lab limits are below JavaScript's maximum exact integer. Use Go `int64` arithmetic even for incoming SQL integer quantities/deltas.

Cart quantities are 1–10,000 and carts contain at most 100 distinct products. On-hand stock remains 0–2,147,483,647. Signed inventory delta is -2,147,483,647 through 2,147,483,647; reject arithmetic overflow and any result below reservations. Cart versions exposed to the client are 1–9,007,199,254,740,991; reject a mutation with 409 `cart_version_exhausted` before its increment would exceed that range. Do not wrap/reset versions.

POST cart item adds the requested quantity to an existing product, while PATCH replaces its quantity. Validate the resulting total against the limit. Every successful mutation locks the parent cart first and increments its version once, including setting an unchanged quantity or clearing an empty cart. Removing a missing/not-owned item returns 404 without incrementing. POST/PATCH return the updated cart; DELETE returns 204 and requires a fresh cart read for the new version. Cart items do not reserve inventory; active products can be added without sufficient current stock, and checkout performs the definitive check.

Cart GET holds a shared parent lock through the item read; every writer holds an exclusive parent lock through its item changes, version increment, response snapshot, and commit. Adding or replacing quantity requires an active product, held with a shared product lock so retirement serializes with the change; retired items can still be removed or cleared. A missing/inactive product returns 404, an excessive resulting quantity 422, and a new distinct product beyond capacity 409 `cart_full`. At version exhaustion all attempted item changes roll back together with the rejected increment. Read/list responses expose only the fields in OpenAPI, without computed cart prices; authoritative money multiplication/summation remains checkout work.

Product creation inserts its zero-stock inventory row in the same transaction. Inventory adjustment locks the inventory row, adds the signed delta in Go int64, validates the SQL INTEGER range and reserved floor, then writes on-hand quantity without changing reservations. Zero delta is valid. Retirement is a soft update and repeated retirement of an existing product succeeds. Product PATCH may reactivate a product. Optional image URLs may not contain credentials and are never fetched.

**Reason:** Explicit bounds avoid integer overflow and frontend precision loss. Add-versus-replace semantics and one version increment per mutation make checkout races testable.

## 11. Idempotency encoding and locking

Require a 1–128 character Idempotency-Key of visible ASCII (`0x21`–`0x7e`), case-sensitive and untrimmed; clients generate UUIDv4 keys. Store one retained intent hash in `checkout_idempotency.request_hash`; do not add a second full-snapshot fingerprint column.

The canonical intent bytes are compact UTF-8 JSON emitted from a fixed-order typed structure, with fields in exactly this order: `user_id`, `cart_id`, `cart_version`, `shipping_address_id`, `payment_scenario`. Use lowercase hyphenated UUIDs, an integer decimal version, fixed lowercase scenario, and no trailing newline. Store lowercase hex SHA-256. On a repeat key, obtain the original cart ID from the referenced order, not today's mutable cart. Compare intent before validating today's address/cart/products. Original address edits/deletion, product changes, and cart clearing do not invalidate an identical retry. Persist the resolved address/item/price snapshots in the order, without a redundant snapshot hash.

For T1 serialization, SHA-256 the UTF-8 bytes `ecom:checkout:v1:` followed by canonical user UUID, `:`, and the exact key. Interpret digest bytes 0–3 and 4–7 as big-endian signed int32 values and pass them to `pg_advisory_xact_lock(int,int)`. Always recheck the full user/key record inside that lock; collisions only serialize unrelated requests. Acquire advisory lock, cart row, then inventory rows in ascending UUID-byte order. All cart writers use the same cart lock protocol.

**Reason:** The intent remains reproducible after checkout consumes the cart, and the database uniqueness constraints remain definitive even if advisory digests collide.

**Tradeoff:** Keys are retained for the order's lifetime with no cleanup/reuse policy. Advisory hash collisions can add contention without weakening full-key uniqueness. Client retry metadata must preserve the original intent rather than reconstruct it from a cart already cleared by T1; its browser lifecycle remains a [frontend decision](../frontend/IMPLEMENTATION_DECISIONS.md#4-mutations-and-checkout-reliability).

Implementation: [canonical intent and lock identity](../../backend/internal/checkout/intent.go), [T1 and commit resolution](../../backend/internal/checkout/service.go), and [checkout queries](../../backend/internal/db/queries/checkout.sql).

## 12. Checkout transactions, failures, and cancellation

Use READ COMMITTED and guarded conditional updates. The normal flow has three committed database transactions: T1 creates the order and holds; a short claim transaction marks its attempt `processing`; T2 settles. The phrase "two-transaction checkout" names the two business transactions and must not conceal the claim transaction.

Read active products and their snapshot fields in one ordered query; their values at that read are the authoritative checkout snapshot. Later catalog/address edits do not rewrite the order or require commit-time repricing. Reservation quantities/product IDs derive from the same trusted order-item inputs; expiry timestamps equal the order's single captured database creation timestamp plus 15 minutes. Exactly one attempt, number 1, is created for Project 1. `simulator_reference` is the lowercase attempt UUID.

Only `pending` can become `processing` or `cancelled`; only `processing` can settle to `succeeded`/`failed`. Lock order, attempt, reservations by product UUID, then inventory by product UUID for claim/finalization/cancellation as applicable. Cancellation is allowed only before processing is claimed and sets both order and attempt `cancelled`. Matching terminal retries are no-ops; inconsistent terminal combinations are integrity failures, not successful no-ops. All state changes and history occur transactionally. Rejected payment still creates a durable order and returns 201 when settled.

Claim/finalization/cancellation validate the full graph before a write or terminal no-op: attempt identity/scenario/reference/timestamps, order/item totals and reservation links/quantities/deadlines/statuses. After acquiring inventory locks, fresh READ COMMITTED queries compare reserved counters with active-reservation sums. Supported reservation writers take the corresponding inventory locks first. Internal settlement/recovery can finish an inactive owner's committed order; customer HTTP requests still require active-session authorization.

Retry only recognized PostgreSQL SQLSTATE 40P01/40001, up to 3 total transaction attempts, with bounded jittered backoff of 25–100 ms and within the request deadline. Do not retry business conflicts, validation failures, or arbitrary transport errors. Retry each transaction using the same durable identities; never rerun T1 after a known commit as a new order.

An acknowledged rollback before T1 commit guarantees no partial order. A transport error while COMMIT is in flight has an uncertain outcome: inspect the retained user/key with a fresh connection and bounded wait, accounting for the prior transaction finishing. If found with matching intent, return the existing order; if certainty cannot be established, return 503 `checkout_outcome_uncertain` and direct the caller to retry the identical key/body. Absence during a race is not proof of rollback. Do not report 202 unless a committed pending order is actually known; process death may produce no HTTP response at all. A failure after the processing claim leaves a recoverable `processing` attempt; no new attempt is created.

Resolution has a separate one-second budget using `context.WithoutCancel` and a healthy connection from the same bounded pool. T1 waits on the original key's advisory lock; after claim/T2 or cancellation, a shared order-row lock waits for unfinished writers before reading current state. Known new terminal/pending orders return 201/202. T1 resolution and same-key replays return 200 without starting simulation. An unresolved cancellation returns 503 `order_outcome_uncertain` and is retried for the same order. Detected corruption returns a safe 500 even if T1 previously committed; it does not erase the order.

**Reason:** Durable processing ownership makes cancellation safe. Commit uncertainty is a transport fact; customer-scoped idempotency resolves it without assuming rollback.

**Tradeoff:** Ordered locks and full-graph validation favor correctness over throughput; deadlocks can still require bounded retries. Simulation holds no transaction open, so T1 and the claim can survive interruption while T2 remains unfinished. The normal API processes only a newly claimed attempt; GET/replay and an observed existing processing claim do not restart it.

Implementation: [processing/settlement](../../backend/internal/checkout/processing.go), [graph guards](../../backend/internal/checkout/graph.go) and [checkout/read orchestration](../../backend/internal/checkout/orders.go). The exact state/HTTP protocol remains in [checkout design](CHECKOUT_DESIGN.md).

## 13. Recovery and diagnostics

From the root, use `go run ./backend/cmd/reconcile --dry-run --limit N` or `--apply --limit N`. Default to dry-run; reject both mode flags together. Default limit 100, range 1–1,000. Capture one database cutoff time per run and visit eligible pending orders with `reservation_expires_at <= cutoff`, ordered by expiry then ID. The limit counts visited candidates, including flagged inconsistencies. Dry-run uses a read-only transaction and performs no claims or state changes; its findings are a snapshot, not a promise of later ownership.

Apply selects one eligible order at a time with `FOR UPDATE SKIP LOCKED` and a per-run cursor, locks its attempt, validates state, claims a pending attempt, and commits before simulation. Already processing attempts can be safely re-derived because the simulator has no side effect. T2 reacquires all required locks and guards settlement. Concurrent runs may compute the same processing outcome; T2 must still settle exactly once. No lease table or long transaction is needed. Inconsistent terminal states are reported, skipped, and cause a nonzero command exit; they are never blindly repaired.

No force-cancel or expiry-release override is implemented. The existing customer cancellation rule remains the only cancellation behavior. Repeated checkout requests and GET polling return current status without triggering payment/recovery. Operators run reconciliation after interruption; it normally becomes eligible after 15 minutes. Tests advance a clock or prepare expired database timestamps rather than sleeping 15 minutes.

Run multi-query diagnostics in a `REPEATABLE READ READ ONLY` transaction, comparing reserved aggregates against active reservation sums, reservation item/product/quantity links, common expiry timestamps, order totals, and order/payment/reservation state combinations. This diagnostic-only isolation differs from the READ COMMITTED write transactions. Diagnostic mismatch does not authorize rewriting counters. Emit bounded structured summaries and audit counters without customer addresses or credentials.

The command uses a two-minute run budget and five seconds per visited candidate. Recovery needs only `APP_ENV` and `DATABASE_URL`, using the runtime login and shared database/TLS validation; it needs no JWT/frontend settings or migration credentials. Existing processing attempts, including those of inactive owners, can be re-derived from the same persisted ID/scenario. Unknown claim/T2 commits are resolved within a separate second using ordered graph locks and validation; unresolved outcomes are reported for a later explicit run, not blindly retried as business writes.

Global diagnostics retain exact finding counts and at most 100 ordered examples. Apply retains the initial diagnostic snapshot in its summary; it is not a post-apply global integrity assertion. Inconsistent candidates advance the cursor and consume the visit limit. SKIP LOCKED may leave earlier locked rows for a later run; zero visits does not prove all eligible work is finished. Nonzero exit reports findings, operation failures, uncertainty, cancellation or output errors. No automatic repair is implied.

**Reason:** Short locks and deterministic replay handle concurrent operators without workers. A read-consistent diagnostic avoids false mismatch reports across concurrent settlements.

**Tradeoff:** Recovery is operator-driven and normally waits for the 15-minute threshold, so interrupted holds may remain unavailable meanwhile. Concurrent commands can derive the same deterministic result; only guarded T2 changes stock/history once. This safety relies on a local simulator with no external financial side effect and must be redesigned for a real provider in Project 7.

Implementation: [command adapter](../../backend/internal/reconcilecmd/command.go), [read-only inspection](../../backend/internal/checkout/recovery.go), [apply/resolution](../../backend/internal/checkout/recovery_apply.go) and [diagnostic queries](../../backend/internal/db/queries/recovery.sql). Commands and output interpretation belong in the [operator guide](RECOVERY.md).

## 15. Milestone 2 implementation details (2026-10-19)

Implement the five T1 steps as one use case in `backend/internal/checkout`, verified in increments. Separately callable reserve/create/consume operations would allow partial business state; `CreatePending` owns their single transaction. The caller supplies the trusted authenticated principal separately from the request. The service verifies that the user is currently active. Customer/admin session authentication remains the existing HTTP boundary; a public body must never choose the actor. The service validates syntactic UUIDs, canonicalizes them for hashing, preserves exact key bytes and accepts only the approved version/scenario bounds.

Use an early read of retained intent, followed by a definitive recheck under the transaction advisory lock. Reconstruct the hash with the original order's cart ID before reading mutable cart/address/product data. `Result.Replayed` identifies all retained results, including commit-resolution results; these must not automatically trigger processing. The idempotency row's `completed` status means T1 completed, not that payment succeeded.

Compute bounded line/subtotals in Go before acquiring inventory holds. Read all product snapshot values in one UUID-ordered query; an inactive product returns service error `product_unavailable` (409 when HTTP is enabled). Invalid monetary bounds return `invalid_checkout_total` (422 when HTTP is enabled). Insufficient stock retains its existing 409 policy. Both scenarios create a pending attempt; simulation still belongs to Milestone 3.

Order creation uses PostgreSQL's single transaction timestamp: default `created_at=now()` and `reservation_expires_at=now()+interval '15 minutes'`. Every reservation receives the returned order deadline exactly. Shipping snapshots use typed fields without the saved address ID and reuse saved-address normalization/validation. Snapshot price/address values do not change after later edits or deletion.

Generate order/payment/history/idempotency UUIDs once per operation; allocate and retain item/reservation UUIDs by product across recognized transaction retries. Retry only 40P01/40001, with at most three total attempts and 25–100 ms jitter within the operation's five-second deadline. PostgreSQL-confirmed COMMIT aborts are retryable by the same rule. Unknown transport/commit errors are not blind transaction retries.

For uncertain COMMIT, acquire an independent healthy connection through the existing bounded pool, start a fresh READ COMMITTED transaction and acquire the same advisory lock before lookup. The failed connection is discarded by pgx. Lock acquisition waits for any unfinished upstream T1, providing the visibility barrier. Lookup has a separate one-second budget using `context.WithoutCancel`, because acknowledgement loss can coincide with request cancellation; cleanup is bounded separately. This adds no extra pool or connections outside the existing pool limit. A matching record returns its durable state; a known conflicting intent returns the idempotency conflict; inability to resolve or absence of a retained key returns `checkout_outcome_uncertain`. Never recreate T1 automatically during resolution or treat a missing record as proof of rollback.

Read mutable order/payment fields in one query, followed by immutable item snapshots, so a future atomic T2 cannot produce a mixed order/payment response. Reject inconsistent order/payment status pairs as integrity failures. The test harness alone wraps actual PostgreSQL sockets to lose acknowledgements before/after COMMIT and delay an unfinished commit. SQL trigger faults test rollback and retry budgets, including deferred COMMIT failure; no public fault flags, background workers, provider integration or new runtime dependencies are introduced.

## 16. Milestone 3 implementation details (2026-10-19)

Keep processing, settlement, cancellation, order reads and HTTP adaptation in the existing `checkout` package, with handwritten `settlement.sql` and generated pgx queries. `Checkout` coordinates T1, the separately committed claim, simulation and T2. The simulator interface accepts only the persisted attempt ID and scenario. Production always uses the deterministic local implementation; only test construction substitutes interruption/blocking behavior. This keeps transaction tests realistic without exposing public fault controls or adding dependencies.

Claim, settlement and cancellation acquire order, payment, product-ordered reservation, then product-ordered inventory locks. Validate the full graph before every write and terminal no-op: one attempt, identity/reference/scenario, legal state/timestamps, item totals and reservation links/quantities/deadlines/statuses. After inventory locks, compare each counter with its active-reservation sum using fresh READ COMMITTED statements. All supported writers lock inventory before changing reservations, making this comparison stable. Corruption returns a safe integrity failure without counter repair or a successful no-op. This intentionally favors correctness over maximizing claim throughput.

Only a claim that changes `pending` to `processing` owns normal simulation. Another caller observing `processing` cannot resume it through `Process`; Milestone 4 will explicitly re-derive such outcomes. Internal claim/settlement operations require a trusted owner identity but can finalize an inactive customer's previously committed order, so future recovery does not strand its holds. Customer HTTP routes still require current active user/session authentication; cancellation and reads also check active actors in their services.

T2 verifies the supplied decision against the stored scenario. Acceptance consumes on-hand and reserved quantities; rejection releases reserved quantities and stores `simulated_decline`. Cancellation releases holds only while the attempt is pending. State changes, timestamps and one history record commit together. History reasons are `payment_succeeded`, `payment_failed`, and `customer_cancelled`. Matching terminal retries validate and return existing state without another stock change/history entry. Expiry never changes an accepted decision.

Use the existing five-second operation deadline across checkout, not a new full budget for each phase. Retry only confirmed 40P01/40001 aborts, at most three attempts per state transaction with stable history identity and existing jitter. After a post-T1 interruption or lost claim/T2 COMMIT acknowledgement, read through a fresh healthy pooled connection with a separate one-second budget and a shared order-row lock. That lock waits for an unfinished writer: no stale T1 snapshot can stand in for unknown current state. Return 202 only for a known pending order, 201 for a new known terminal order, and 503 if unresolved. T1 lost acknowledgements retain Milestone 2's existing-key replay semantics (200, without processing). Process death can yield no HTTP response.

Cancellation also resolves lost acknowledgement by this bounded fresh read. Known cancelled state returns 200; otherwise return 503 `order_outcome_uncertain` and retry cancellation for that same order. This extends the wire contract to cover a real transport failure rather than falsely promising rollback. Repeated checkout keys remain 200 status reads and never start payment work. GET order/payment routes likewise perform no recovery.

Mount all new routes within the existing authenticated chi/CORS/body-limit/logging boundary. Public payment DTOs omit scenario, simulator reference, ownership and internal timestamps. New order lists use the shared strict pagination parser (default 20, maximum 100) and deterministic descending creation time/UUID ordering. Multi-order and payment-history reads use REPEATABLE READ READ ONLY snapshots so settlement cannot mix states within a response. No worker, recovery command, payment provider, new table or runtime dependency is introduced in this milestone.

## 18. Password recovery implementation (2026-10-27)
