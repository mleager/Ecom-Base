## Identity, cookies and admission

- A guest is a distinct UUID principal with one server cart; it has no password, role, account profile or address book. The UUID is an identifier, never authorization. `guest_sessions` stores only SHA-256 verifiers of cryptographically random **32-byte / 43-character base64url** opaque secrets. Existing Argon2id/JWT/account-session policy is unchanged.
- Full guest cookie: `ecom_guest`, host-only, `Path=/api/v1/guest`, `HttpOnly; SameSite=Strict`, `Secure` using the existing production cookie configuration. Only explicit local loopback HTTP may omit Secure. Fixed **30-day** absolute database expiry; no sliding GET renewal. Use database `clock_timestamp()` after lock waits; cookie Expires derives from that deadline.
- `GET /guest/session` restores/verifies; it never creates, rotates or sets cookies. `POST /guest/session` creates only when no cookie is supplied (201), or returns the same valid principal/deadline (200). An invalid/expired/duplicate cookie returns 401 and is not silently overwritten. Browsing creates no guest rows; first deliberate Add/guest-cart entry may bootstrap after account restoration is definitively anonymous. An account-network error is not anonymity.
- `POST /guest/session/rotate` replaces the full credential, revoking its predecessor without changing principal/cart/deadline. Perform under the identity coordinator on deliberate guest continuation across account transitions; resolve an uncertain reply using GET, never automatic rotation replay. `DELETE /guest/session` revokes the presented matching verifier and clears only this guest cookie; an absent/expired/unrecognized single cookie can also be cleared deliberately with 204, without asserting an identity. Duplicate cookies fail closed. This never removes stored intents. Cookie loss after a rotation can lose cart access; retain checkout metadata and offer scoped mailbox recovery. No token grace window or account privilege is granted by a guest cookie.
- All guest responses use `Cache-Control: no-store`; reuse exact configured Origin/CORS, exposed request ID/Retry-After and existing strict JSON decoder/64-KiB ceiling. Every POST/PATCH/DELETE, including public bootstrap/proof requests, requires exact Origin and `X-CSRF-Protection: 1`. Credentialed GET permits an absent Origin for same-origin navigation, but any supplied Origin must match. Cookie calls use `credentials: include`, no bearer, no generic auth replay. Only cart-choice calls intentionally require **both** current bearer/session and guest cookie.
- Duplicate credential cookies and unexpected bearer headers on cookie-only routes fail closed. A malformed/expired verifier cannot authorize anything; an independently valid exact-target recovery grant may still authorize its target despite an unrelated invalid full cookie. Recovery cookies never authorize normal guest-cart/bootstrap/history operations. A target operation may accept a full matching owner or the exact scoped recovery grant described below; it cannot silently substitute another principal. Bodyless routes reject non-whitespace bodies with 400.

Initial single-API budgets (not distributed quotas): bootstrap **5/peer/hour**, guest reads **120/peer/minute**, writes **30/peer/minute + 30/guest/minute**, rotation **5/guest/hour**, preparation **5/guest/hour**, mail **20/peer/minute + 3/canonical-email-and-target/hour**, redemption **20/peer/minute + 5/token-hash/minute**. Derive peer from RemoteAddr, not untrusted forwarding headers. Reuse bounded 10,000-entry in-process limiter maps, fail closed at capacity; body/peer/global admission precedes target lookup. At most **32 admitted guest writes/mail requests** concurrently; saturation is 503 with Retry-After 5, peer throttling 429 with the remaining window (1–3600 seconds).

Cap live full guest sessions at **10,000** under a short dedicated creation advisory lock; expired/revoked sessions do not count. One prepared intent per guest, at most 100 intent/tombstone rows per guest, and at most three live mail proofs per target. Per-owner limits are serialized in PostgreSQL; no timestamp-dependent partial index. These are portfolio resource limits with explicit capacity errors, not claims of unlimited anonymous resilience.

## Cart ownership and sign-in choice

Guest cart bodies/responses and quantity/version/capacity bounds reuse current Cart DTOs: 100 distinct products, quantities 1–10000, positive safe-integer version through 9007199254740991. Adding does not reserve stock or cap against observed availability. Parent-lock/version increment, item-ID ownership, post-204 rereads and uncertain-write readback remain mandatory.

Account authentication and guest credentials remain disjoint. Login never adopts a cart or guest orders. After login, verify both identities and read both carts. If a nonempty guest cart exists, show **Keep account cart** or **Use guest cart** before new account shopping mutations. Even an empty account cart requires deliberate adoption. If no guest cart exists/it is empty, use the account cart; no transfer is inferred. Browsing/account/security remain usable while a choice is pending.

If the account is verified but the guest cookie is missing/unverifiable, do not invent an empty guest cart or call the two-credential transfer API. Offer deliberate **Continue with account cart**, preserving inaccessible guest metadata and disabling adoption. This selects an already-authorized independent account cart; it does not prove anything about the old guest. A guest restoration failure must not turn an authenticated shopper into a new anonymous principal.

`GET /guest/cart-choice` requires bearer + full guest cookie and reports required/completed choice and current versions for that account session. `POST /guest/cart-choice` captures `choice: keep_account | use_guest` and both expected versions:

- `keep_account` records the decision for that account session/guest-cart version; both carts remain unchanged.
- `use_guest` atomically copies guest lines into the existing account cart, **replacing** its contents, clears the guest lines and increments each affected cart once. Do not reparent carts/items/orders or merge quantities. Preserve item quantities, enforce capacities, and allow unavailable existing lines to remain removable. No inventory adjustment/reservation occurs.
- Recheck both sessions, owners, versions and active guest intent under locks. Version mismatch is 409 `cart_choice_conflict` with no transfer. An unresolved/prepared guest intent blocks `use_guest` with 409 `guest_checkout_unresolved`; `keep_account` may select the independent account cart without modifying that intent. Browser unreadable recovery state blocks transfer. Existing pending known orders are not an indefinite transfer/purchase lock.
- Save the receipt in `guest_cart_choices` keyed by account session + guest principal; bind the guest version and choice, not an email or access token. Peer tabs reread it. A changed guest cart/session requires a new choice; ordinary account-cart edits do not. Timeout/500/503 is uncertain: reread choice and both carts; never repeat replacement automatically.

Store the submitted version tuple/choice and resulting versions with that receipt. An identical already-committed submission may return its confirmed choice plus a fresh current account cart without incrementing again; a different or stale submission cannot overwrite a newer choice. This server-side duplicate guard complements the send-once browser path.

Task 4 implementation clarification: once a receipt matches the current guest-cart version, only its identical original submission can be repeated. A competing different choice conflicts even if `keep_account` left both versions unchanged. A new account session or actual guest-cart version change opens a new decision; ordinary account-cart edits do not. This prevents a late Use guest response/request from overturning an already confirmed Keep account choice.

Auth logout revokes only the account session and clears private UI. Restore a dormant full guest credential under the identity coordinator, then deliberately rotate it before guest writes; never copy account cart/orders back. Account replacement clears drafts/selection, preserves each owner's recovery slot and reruns choice. Same-owner return restores only after verification. Guests remain guests after registration; registration does not attach prior orders. An explicit `DELETE /guest/session` is not a way to erase unresolved browser recovery.

## Guest preparation and immutable checkout

Paths/body shapes are in the addendum. Preparation is necessary to keep private shipping out of persistent browser storage.

1. Review current guest cart plus contact/US shipping and an explicit `accept` or `reject` choice. On deliberate Place generate separate UUIDv4 intent ID, idempotency key and generation. Persist/read back a guest v2 `preparing` record **before any preparation or checkout POST**; persistence/coordination failure prevents sending.
2. `POST /guest/checkout-intents` uses the original Idempotency-Key and `{id,cart_version,payment_scenario,contact_email,shipping_address}`. Canonicalize existing email/text/US rules and store immutable shipping/contact, source cart, version, scenario, key and payload hash. It creates **no order, hold, payment or cart mutation**. Return 201 on first preparation, 200 for an identical existing preparation; different payload/key binding is 409 `idempotency_conflict`. Do not re-prepare an existing ID from changed UI fields.
3. Validate returned owner/ID/key/reference and canonical shipping; persist/read back `unresolved` before `POST /guest/checkout` with the same key and immutable `{cart_version,checkout_intent_id,payment_scenario}`. Both POSTs may run within the original deliberate action, under its bounded lock. Interrupted preparation never automatically continues after restore/renewal.
4. A preparing record after navigation/lost reply offers an explicit server read by original ID. Prepared state recovers the original fields from the server and enables deliberate original-checkout Resume. GET 404 is **not** permission to replace the ID: a delayed preparation could still arrive. The explicit retire endpoint below supplies a fence.
5. Preserve T1's existing owner/key lock → replay lookup → parent cart/version → UUID-ordered inventory → snapshots/payment/history/idempotency/cart clear. For guests prepend the guest-principal lock and lock the immutable intent before the cart. Retained committed replay is checked **before** expired/retired preparation refusal or current-cart validation. It never restarts interrupted payment processing.

Direct shipping has required `recipient_name`/`line_1`/`city`/`region`/`postal_code`, optional `line_2`, and materialized `country_code: US`; no label, address ID, account or address-book row. Reuse 200/200/100/2/10 code-point limits, valid Unicode/no NUL/trim rules and US state/DC/ZIP validation. Contact email reuses current lower-case/trim/254-UTF-8-byte parsing; no provider alias normalization. Guest preparation freezes these supplied shipping values; **prices/stock remain authoritative at T1**, not preparation. Account saved-address behavior is unchanged.

The guest fingerprint is versioned separately from the unchanged user canonical bytes: bind guest principal, source cart/version, intent ID, scenario and stored canonical payload digest. Retain the digest/reference after private draft cleanup, so known-order replay remains verifiable. Never recompute an old user's hash using a new structure.

Preparation lifetime is **30 days**. On expiry, under owner/key locks first check for a committed order; otherwise mark expired, disallow new T1 and scrub plaintext contact/shipping. This is a new guest pre-commit refusal, **not local intent expiry**. Keep its small ID/key/hash tombstone and a SHA-256 canonical-email matching digest for scoped recovery of the closed outcome. The digest is not authorization: a new single-use mailbox proof is still required, sent only to matching canonical input. It stays server-side and is never exposed in the API/browser. An existing order remains replayable/observable. Local timestamps never authorize deletion or replacement.

`POST /guest/checkout-intents/{id}/retire` uses the original key. Under owner/key/intent/cart coordination: return authoritative known order if one committed; otherwise close the intent, or insert a **retired tombstone for an absent preparation**, then commit a 200 retired receipt. Late preparation/checkout cannot resurrect it. Ambiguous retirement preserves local state and requires explicit read/retirement resolution. A generic 404, 401, malformed response or timeout is never such a receipt.

## Outcome, handoff and observation

|---|---|

| Preparation/checkout timeout, lost/malformed reply, 500/503, generic 401/403/validation | Preserve original record/key/body and phase; suspend or explicitly recheck. No transport, navigation, authentication or timer replay. |
| 409 `idempotency_conflict` | Preserve/block; never substitute a key, intent, shipping or scenario. |
| `stale_cart`, `insufficient_inventory`, `product_unavailable`, `empty_cart`, `cart_version_exhausted`, `invalid_checkout_total` | Guest path must resolve committed lookup under the original key before persisting/returning a definitive `rejected` intent state. Then offer explicit server retirement and fresh review. User path retains its current verified classification. |
| Guest `checkout_intent_expired` / `checkout_intent_retired` (409) | Definitive only with valid matched closed-intent receipt and protected no-order check; retire deliberately. `checkout_intent_not_found` (404) alone is insufficient. `address_not_found` remains account-only. |
| Unsuccessful order read or exhausted observation | Keep the known locator and last verified state; offer manual Check Status. Never infer rollback/payment failure or return to checkout replay. |

New proposed codes: 401 `guest_session_unavailable` (full credential) / `guest_recovery_unavailable` (scoped grant), 400 `invalid_guest_authentication` for unexpected bearer, 409 `guest_capacity_exhausted` / `guest_checkout_unresolved` / `cart_choice_conflict`, and 503 `guest_capacity_unavailable` / `guest_outcome_unknown` (non-checkout write COMMIT unknown). Duplicate full cookies use the same unavailable-credential response. Existing `csrf_rejected`/`origin_rejected`, `rate_limited`, commerce bounds/ownership errors and financial uncertainty codes remain. These codes never authorize a new checkout or prove a prior one rolled back. Mail proof invalidity remains `invalid_guest_proof`; SMTP delivery-off is globally `email_delivery_unavailable`, with nondisclosing 202 for target-specific suppression/send failure.

Record guest business rejection only after rolling back any partial T1 work, reacquiring the same owner/key locks and resolving a possible winner; return its Order if one committed, otherwise commit the closed rejection state. If that resolution/commit is uncertain, use 503 `checkout_outcome_uncertain`, never a definitive rejection. Late same-key work sees the closed state. Cart unique source-version protection remains additional defense.

T1 consumes the cart for both scenarios. Acceptance consumes reservations; rejection records `payment_failed`/payment `failed` and releases reservations, **without refilling the cart**. Existing claim/T2/cancellation graph, one attempt, guarded settlement and operator-only reconciliation stay shared. Guest metadata cleanup cannot settle, cancel or release inventory.

Use a trusted internal `user | guest` owner (and a separate scope authorization check at HTTP boundaries), retaining existing user service wrappers/hash bytes. Operator candidates derive that owner from validated XOR database columns, never a request-supplied ID. Adapt user-filtered graph/load/settlement queries so guest orders follow the same financial engine; do not fork payment processing or require a live guest cookie for post-commit settlement/reconciliation. Tests must cover mixed owners, expired guest credentials, NULL user_id and unchanged user replay hashes before exposing guest checkout.

`known_order` in the recovery slot is the durable handoff; retain it through navigation/failing storage and reads. Invalidate/refresh the full guest cart after releasing checkout locks. New checkout needs a fresh cart read/review and deliberate replacement of that exact known record. A scoped recovery grant cannot read/modify the old full cart: it can observe its known order; future shopping uses a separately verified full principal and fresh cart, never transferred metadata.

Budgets: lock acquisition **5s total**; preparation POST **10s**, checkout POST **30s**, one combined action at most **40s** plus acquisition; other commerce writes **20s**, GET **10s**. Clip cancellation, lifetime and stale-result checks to these deadlines. Existing observation remains one read in flight, **3s after completion**, **60 elapsed seconds or 20 actual reads**, overall timeout aborting an in-flight read. Stop on terminal/navigation/identity/page inactivity; manual Check Status never restarts the automatic window or backend processing.

## Scoped mailbox recovery and delivery

Lost full credentials cannot be restored by email alone. `POST /guest/recovery-requests` accepts contact_email and **exactly one** checkout_intent_id or order_id. It always gives the same 202 receipt for eligible/ineligible/expired/unknown targets; target/address quota suppression also returns that receipt. Public peer 429 and global delivery-off/admission 503 are independent of target eligibility.

For a matching retained order or prepared/closed intent with matching contact digest, create a hashed 32-byte proof bound to **one target, guest principal, purpose and snapshot email**. Fifteen-minute expiry, at most three live proofs per target, single-use atomic redemption; no links for unrelated orders sharing an email. Closed-intent proofs may only read/retire that closed outcome, never recreate its expired shipping. An absent preparation cannot be recovered by claiming its email. If the full credential is also lost before preparation ever reached the server, there is no safe self-service proof of the old owner: preserve/block the old slot and require operator-assisted resolution rather than inventing credentials or silently discarding it. Other-browser/data-loss limitations still apply.

Use existing standard-library SMTP configuration/TLS validation, trusted `FRONTEND_ORIGIN` and **2s** send deadline. No new credentials, provider, queue, retries or mail preview endpoint. Link is `/guest/recover#token=…`; capture into page memory and remove the fragment before mounting external resources. GET/link scanners consume nothing. Never log token/email/address/message bodies or include them in metrics. Request handling uses an **8s response floor** after admission, within a 10s server budget (lookup ≤5s, SMTP ≤2s); padded ineligible/failure paths reduce eligibility timing differences. Client ceiling remains 20s. Cancellation does not prove that mail/token issuance rolled back.

`POST /guest/recovery-confirmations` consumes a valid proof and issues `ecom_guest_recovery`: same host/path/HttpOnly/SameSite/Secure rules, **30-minute absolute** grant, SHA-256 verifier only. Scope is `checkout_intent` or `order` with exact target. It never logs in a user, replaces the full guest cookie, grants all orders for an email, adopts a cart or revokes another account. Replace/revoke only the previous recovery cookie presented by this browser, not other people's grants. Generic 400 `invalid_guest_proof` covers invalid/wrong-purpose/expired/used/stale proofs.

`GET /guest/recovery-access` verifies that grant and returns its nonsecret principal/scope/target/deadline; `DELETE` revokes/clears only it. An uncertain confirmation is resolved by this GET if the cookie landed, otherwise request another proof; never repeat a used token automatically.

- Order scope permits **only** matching order detail/payment/cancellation, never order history or another order.
- Intent scope permits **only** its GET/retire, original same-key checkout and the resulting order detail/payment/cancellation. It cannot prepare new shipping, change scenario, read/edit the full cart, list orders, or mint another principal.
- Target routes may accept either a full matching guest owner or this matching scope. Normal guest-cart/history/choice endpoints require the full credential. Keep recovered view/context separate from active guest/account cart state; an unrelated active guest cookie or bearer session cannot broaden the grant.
- Controlled TLS SMTP tests plus actual mailbox receipt, token use, scanner/no-GET consumption, expiry/reuse and uncertainty proof are Task 5 gates before dependent UI acceptance. Guest receipts are best-effort notification after a known T1 commit; SMTP failure cannot roll back/relabel checkout. Users may request scoped recovery by their retained intent reference if the receipt was lost.

## Browser persistence and coordination

Guest v2 uses `commerce-lab:checkout:<encoded-api-base>:guest:<uuid>:v2` for its slot/owner lock, with the same canonical API-base resolver/encoding as v1. User v1 slot/name/parser/bytes stay supported unchanged. Cart locks are `commerce-lab:cart:<encoded-api-base>:<user|guest>:<uuid>`; retain the existing API-scoped auth lock/channel and checkout change-only channel. Do not rewrite or delete old records merely to upgrade. A guest record is canonical strict JSON, at most **4096 UTF-8 bytes**, exactly:

`schema_version:2, owner_kind:"guest", owner_id, idempotency_key, request:{cart_version,checkout_intent_id,payment_scenario}, created_at, generation, revision, phase`; only `known_order` adds order_id. Phases: `preparing | unresolved | rejected | known_order`. UUIDs are lower-case canonical; key/intent/generation use distinct crypto.randomUUID values, revision positive safe integer, timestamp canonical informational ISO milliseconds, version within current safe bound. Unknown fields/schema/phase, wrong owner, corruption/storage unavailability or unexpected mutation preserves bytes and blocks new checkout. No PII, credentials, hashes of shipping, token or speculative result is permitted.

Restore only after full guest/session or exact recovery-scope verification. Owner is a tagged `user | guest` identity; matching raw UUIDs across kinds are not interchangeable. Different account/guest/recovery targets clear active private UI, abort queued/obsolete reads and ignore late callbacks, preserving stored intent. End-of-cookie lifetime does not retire it. Browser/profile/data loss and another device can remove the locator; mailbox/order recovery still requires proof, and exact identification without a reference is not guaranteed. Same-origin JavaScript/browser-profile access can read local metadata; scoping is not encryption.

To avoid silently bootstrapping a replacement owner after cookie loss, retain one nonsecret hint at `commerce-lab:guest-checkout-hint:<encoded-api-base>`: strict canonical `{schema_version:1,guest_id,checkout_intent_id,generation}`, UUIDv4 values, ≤256 UTF-8 bytes. It carries no key/request/PII/credential. Write/read back this hint **before** the v2 slot, and confirm both under the owner lock before either POST. A partial/unknown hint write fails closed. With no verified full guest, hint presence/corruption blocks new guest checkout/adoption and offers generic recovery; it does not restore/display another record. An explicit email-recovery request may use that untrusted target identifier, but only server matching plus mailbox proof grants access. Never enumerate/publish old guest slots or treat the hint as authority.

After verified known-order handoff plus fresh cart read, remove only the matching hint (guest/intent/generation), retaining the known-order record. After authoritative retirement, remove the matching slot and hint with readback. Failed/unknown cleanup blocks replacement. Logout/end clears private UI/credentials without deleting a hint for an unresolved attempt; it must remain possible to end a session for privacy. Independent verified account shopping can continue without adopting the inaccessible guest cart. A new guest owner is never automatically minted to bypass a retained hint. This is a browser coordination guarantee; cleared browser data/noncooperating clients remain the stated limitation.

Keep existing `/cart`, `/checkout`, `/orders` and `/orders/:id` screens behind an owner-aware commerce boundary; account/profile/address/admin routes remain account-only. Normal account restoration takes precedence for those shared routes. Add minimal `/guest/recover` for explicit request/fragment-proof confirmation, `/guest/checkout/:intentId` for verified scoped original-intent resolution, and `/guest/orders/:id` for explicit guest/recovered order detail. These guest views verify full/single-target access independently and never switch or populate the unrelated account cart. No guest token goes in a URL/query; order/intent IDs identify targets only. Guest client/controller hooks compose with existing auth/cart/recovery controllers and request budgets; no second router, state framework or global identity fallback is added.

Use existing Web Locks + BroadcastChannel; no fallback writes when unavailable. Notifications contain only fixed change-event strings, never owner/key/cart/token/address metadata, and trigger verified locked rereads.

1. Extend the **existing API-scoped auth identity lock**, rather than creating an independently nested guest/auth lock, for bootstrap/rotate/end/login/logout/proof-cookie transitions. Bound new guest lock acquisition to 5s; preserve existing auth behavior. Never hold it while waiting for checkout/cart locks.
2. Checkout uses one **tagged owner** lock; reread persistence and verify pinned owner/session revision/deadline after acquisition and before each send. Hold through bounded preparation/checkout plus resulting persistence, not observation. Resolve/renew identity outside the lock and require another explicit action.
3. Guest cart mutations use a per-owner cart lock (5s acquisition, 20s write). Within that bounded write, acquire the existing identity lock last, reverify the guest and pin the cookie through send. Cookie-only mutations carry no expected owner ID. The final identity stage prevents a cooperating tab from replacing the cookie between verification and transport. Identity-only operations release that lock before acquiring any commerce lock. Keep cart and checkout locks separate for single-owner operations. Server versions handle a concurrent cart change during checkout. Refresh/invalidate cart after releasing checkout coordination.
4. Explicit cart choice is the sole multi-owner operation. Verify both identities outside locks, acquire both checkout locks in lexical full-name order and then both cart locks in lexical order, within **one 5s acquisition budget**. Reread both recovery slots before replacing a cart. Acquire identity last within the bounded write, recheck the guest credential and current choice versions, then send once without awaiting auth renewal. Release in reverse order.
5. All updates/retirement/replacement match owner kind+ID, key, generation and revision. Cancel acquisition/lifetimes on identity/navigation/inactivity; stale callbacks cannot overwrite/delete/resurrect records. Persist known order before navigation and retain the locator after failed readback.

## Admin search contract

`GET /admin/products?q=…&is_active=…&limit=…&offset=…` remains bearer/admin only. Accept only one of each key, valid query encoding, existing limit 1–100/default 20, safe offset and `true|false` activation grammar. UI offers 20/50/100. Normalize q using the existing Go trim/valid-Unicode/no-NUL/≤200-code-point rules; absent/trimmed empty means no text filter. Malformed encoding/duplicates/unknowns return 400, valid-shaped out-of-range text 422.

Use parameterized literal substring ILIKE on **name OR SKU**, escaping `!` then `%`/`_` with `ESCAPE '!'`; preserve backslash as a literal and parentheses around optional activation plus text predicates. Match the full eligible dataset before LIMIT/OFFSET, preserve `p.name,p.id` and existing availability/integrity semantics. No full-text/search service, pg_trgm, suggestion API, relevance ordering, fetch-all, count endpoint or new index is required for the portfolio dataset.

Share InputGroup/Input/Button and normalization with catalog, but use separate context/submit handlers and typed URL adapters. Apply filters commits q/status/limit together and resets offset; preserve them in detail/edit/inventory return links and browser history. Previous/Next and derived current page only; an empty later page still permits Previous. Never use the public endpoint to implement admin search or leak inactive products publicly.
