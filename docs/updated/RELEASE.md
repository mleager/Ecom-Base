# Release 1.0.0 (`ecom-base`) — Project 1 base

The first release of Project 1 of the Commerce Reliability Lab: everything from Milestones 1–17 and the review fixes that followed. It is tagged **`base-v1.0.0`** and published as **`ghcr.io/mleager/ecom-base:1.0.0`** (digest below once published). Scenario projects run this image, or fault variants of it published as `ghcr.io/mleager/ecom-<variant>`; the image's `io.github.mleager.ecom.variant` label is `base`.

## Version history and naming

Earlier local tags were renamed when the base was released, before anything was pushed, so `1.0.0` is the only release name:

| Tag | Commit | What it is |
| --- | --- | --- |
| `base-v1.0.0` | the release commit | **Release 1.0.0**, image `ecom-base:1.0.0` |
| `m17-cdn-alb` | `2c31cf4` | Milestone 17 marker (formerly the local tag `v1.1.0`) |
| `m16-baseline` | `a8c16a2` | Milestone 16 marker (formerly the local tag `v1.0.0`) |

The local tag `v1.1.1` was dropped: its content is release 1.0.0. Older documents (task logs, milestone records, decisions) keep the old names as written at the time.

## What the release contains

- One image that serves the API and the built React app from one HTTPS origin, plus the `migrate`, `reconcile`, `maintain` and `db-bootstrap` commands (Milestones 1–16; details in the Milestone 16 section below).
- Ready for a CDN and several API tasks: trusted CloudFront viewer address, PostgreSQL-shared rate limits, IPv6 prefix limits, guest idle expiry, refresh-token reuse detection, and a Terraform development stack on AWS (Milestone 17; see that section below).
- The fixes from the 2026-11-19 database and Terraform reviews (M17 tasks 14–19), listed next.

## Changes in the last round before release (M17 tasks 14–19)


| Area | Change |
|---|---|
| Role passwords | `db-bootstrap` sends PostgreSQL only SCRAM-SHA-256 verifiers it computes itself, so a failing `ALTER ROLE` can't put a password in the server log (on RDS, kept for days). Role passwords must be printable ASCII. `init.sh` turns statement logging off for its own session. |
| Role timeouts | `ecom_app` has role defaults for `statement_timeout` (5 s), `lock_timeout` (2 s) and `idle_in_transaction_session_timeout` (30 s), a server-side backstop for sessions that don't set them. |
| Local database | `compose.yaml` pins `postgres:16-alpine` to the deployment's digest (PostgreSQL 16.15). The deployment's `pg_hba` admits only `ecom_migrator` and `ecom_app` to `ecom` over the network. |
| AWS rollout | The apply waits for the API service to reach steady state, so a circuit-breaker rollback fails it; the SPA is published only after the new API tasks serve. |
| AWS health check | The target group checks `/health/live`: a database outage no longer makes ECS replace every API task. |
| AWS instances | Optional `ecs_ami_id` pin; a rolling instance refresh with ECS managed draining replaces the instances when the launch template changes. |
| Terraform settings | The committed tfvars leave `domain_name` unset; personal settings go in a gitignored `local.auto.tfvars` (example checked in). |
| Docs | Terraform README "Known limits": internal certificates renew only on apply, six task slots, outages show as `500 internal_error`. |

Moving a database from the `m17-cdn-alb` milestone build: no migrations (schema 16). Pull the pinned PostgreSQL image (`docker pull postgres:16-alpine@sha256:0cefaabd…`). An existing local volume keeps working; add the `ecom_app` role defaults once with the command in [backend/DATABASE.md](backend/DATABASE.md). On AWS the next apply re-runs `db-bootstrap`, which sets them.

## Run it on a fresh machine

Tested on Ubuntu 24.04 with the tools above. Needs:

- Docker Engine with Compose v2 and Buildx (BuildKit), Bash, Git, OpenSSL and curl.
- Ports 8443 (app) and 8025 (captured mail) free on `127.0.0.1`.
- Network access for the first build (base images, npm and Go modules).

Go, Node and PostgreSQL on the host are not needed to run the release.

```bash
git clone <repository-url> ecommerce && cd ecommerce
git checkout v1.0.0
bash scripts/certs.sh                 # local CA plus server, postgres and mail certificates (.cache/certs)
bash scripts/dev.sh init-deploy-env   # .env.postgres, .env.migrate, .env.deploy (mode 0600, new secrets)
bash scripts/dev.sh deploy            # build the image, start, wait for a ready API
curl --cacert .cache/certs/ca.pem https://localhost:8443/health/ready
```

Then open `https://localhost:8443` (trust `.cache/certs/ca.pem` in a separate browser profile; production mode sends HSTS for `localhost`) and read captured mail at `http://localhost:8025`. No mail leaves the machine. Stop with `bash scripts/dev.sh deploy-down` (keeps the data) or `docker compose -f compose.deploy.yaml down -v` (removes it).

bash scripts/release-evidence.sh 1.0.0 release-evidence.md   # builds ecom:1.0.0 from the commit (refuses an existing tag)

## Known limits

- **No registry digest yet.** The portfolio plan publishes `v1.0.0` to GitHub Container Registry, pinned by digest. This machine uses Docker's classic image store, so a local image has only its image ID (the config digest). The registry's manifest digest exists only after a push, and pushing is not done in M16 so far.
- **Builds are not bit-for-bit reproducible.** Two builds of `e8bef0e` produced `sha256:92b64cbe…` and, after a `--no-cache` build refreshed the layer cache, `sha256:e51ebd72…`. The recorded digest identifies one build, so consumers must pin that digest, not rebuild the tag. `release-evidence.sh` therefore refuses to replace an existing `ecom:<version>`.
- **Local certificates.** The release ships none; `certs.sh` makes a local CA for this machine. Real deployments bring their own (M17 moves public TLS to CloudFront and the load balancer).
- **Secrets in env files** are visible to anyone who can run `docker inspect` on the host ([DECISIONS.md](DECISIONS.md#packaging-milestone-16)).
- **No in-container health check** (distroless has no shell or curl); probe `/health/ready` from outside.
- Single host only; multi-instance scaling is [Milestone 17](MILESTONE_17.md). Remaining application limits: [STATUS.md](STATUS.md#known-limits).
