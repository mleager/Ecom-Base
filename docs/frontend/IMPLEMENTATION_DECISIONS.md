## 1. Stack and ownership

Use Vite, React and TypeScript. Keep application/routing/session composition separate from feature areas (auth, catalog, account/addresses, cart, checkout/orders, admin) and shared UI/API utilities. Use the locally installed Node 24.20.0/npm 11.19.0, the [verified exact toolchain](TOOLING.md) and declarative React Router. Native fetch, React context/hooks and CSS Modules/shared variables cover the current requirements without another state/HTTP/UI framework. The [UI design](UI_DESIGN.md) owns routes/layouts; M7 task 1 creates application configuration and the npm lockfile, while task 2 introduces routing/API composition.

**Reason:** Clear feature boundaries help testing and maintenance without introducing a framework/service for every concern.

Task 1 uses a single strict, no-emit TypeScript configuration covering application, tests and runner configuration. Vitest and Playwright have separate discovery patterns; neither accepts an empty suite. A minimal welcome page supplies a real React/component/build check without advertising unfinished shopping controls. Browser artifacts are disabled by default; Vite publishes only `fixtures/public`. Existing EditorConfig conventions are extended to frontend file types instead of adding an unselected lint/format dependency.

## 2. API boundary and state

Centralize base URL/configuration, typed request/response handling, safe errors, credentials and request cancellation. Maintain DTOs at one boundary against the shared OpenAPI contract with contract tests; no generator is selected for this scope. Browser fetch is sufficient for the initial HTTP boundary; an additional HTTP library needs a concrete reason.

Distinguish server-owned data from local form/navigation state. Revalidate or replace affected server data after mutations and clear private cached state when the user changes/logs out. The backend owns prices, cart versions, authorization and state transitions. UI totals are estimates until checkout returns immutable order totals. Display only values supported by the real contract.

**Reason:** One integration boundary keeps refresh/error semantics consistent and prevents stale UI from becoming business authority.

Task 2 implements only the auth/profile DTOs needed next, with response guards and focused OpenAPI source/type checks; other domain contracts arrive with their features. No YAML parser/generator dependency is added. The transport sends credentials/CSRF headers only for cookie operations, omits cookies on bearer/public calls, disables caching/redirects and exposes cancellation. It preserves safe HTTP errors/Retry-After metadata and distinguishes transport/protocol/cancellation failures from definitive 401. It performs zero automatic retries or refreshes; task 4 adds coordinated session policy above it. A malformed/lost success must never become evidence that a mutation rolled back.

The shell exposes home/signup/login, a read-only account page, an administrator access landing and missing-page recovery, with title/heading focus and a keyboard skip link. Its shared header supplies product search; cart/orders/product-management links arrive when functional. Back/forward retains router URLs without forcing a top scroll on POP; complete feature scroll/query behavior is verified with those pages. Shared forms remain native HTML with labelled inputs, described errors and a focused summary; feature modules own submission state.

M8 task 1 extends the shared boundary with public `GET /products` and runtime-validated Product DTOs. Reject malformed, inactive, duplicate or oversized results rather than silently presenting a partial successful catalog. Public reads omit cookies/bearer/CSRF and run independently of session restoration so browsing remains anonymous. Each load has a ten-second deadline, aborts on navigation/unmount and ignores late responses; failures require explicit read retry.

Use a fixed page size of 20 and canonical URL `q`/`offset`, preserving the API's name/ID order. Full pages offer Next; later pages retain Previous even when empty. No total count is available, so none is inferred. Reserve safe-integer headroom for range/next arithmetic and reject repeated, malformed or unsupported query keys. Product names link to details; cart controls arrive in M9.

Render integer cents with a shared USD formatter and show observed in-stock/out-of-stock status without reserving or guaranteeing stock. One primary HTTP(S) image uses no referrer; missing, credential-bearing or failed sources render a labelled fallback. CSS Modules provide the specified one/two/four-column grid. These choices need no new dependency, image service or backend contract.

M8 task 2 uses public `GET /products/{id}` on every detail entry/reload rather than retaining a card snapshot. Validate UUID syntax before transport, validate the returned identity/active state, and reject an incoherent 200 as a protocol failure. Invalid IDs/unsupported detail queries fail locally; real 404 responses share one missing/retired view, while transport/server failures offer explicit retry. The listing and detail pages share one bounded-read hook to keep cancellation, deadline and late-response handling consistent. Description/image fallbacks remain explicit, and description text is rendered as text, preserving line breaks.

Keep only the catalog query string in card navigation state, validate it before forming Back to products, and default direct visits to `/`. This preserves the submitted search and offset without trusting an arbitrary history destination or caching product data. Guest login accepts only a query-free UUID product return path and never performs an implicit purchase. Reuse the money/image/availability presentation; a single column becomes image/content columns at 1024px, with no purchase panel before M9.

M8 task 3 submits the header's labelled native search form explicitly; typing alone performs no read or local filtering. Each submission resets offset to zero; an empty term or Clear search returns to browsing. The URL is the submitted state, restored on back/forward/reload; failures retry that same filter. Search uses the existing public list endpoint and its literal name/SKU matching, with no suggestions, categories, ranking or new service.

Use one pure shared query module for the form, API boundary, paging, detail returns and auth return validation. Trim Unicode White_Space to match Go strings.TrimSpace (including U+0085, excluding BOM), count at most 200 code points after trimming, and reject NUL/lone surrogates before encoding. Strictly decode browser queries before URLSearchParams to reject malformed escapes/UTF-8 instead of silently replacing them. Match the server's semicolon grammar; percent-encoded punctuation remains literal and is encoded once. This keeps all navigation/transport consumers consistent while retaining the existing bounded-read/cancellation policy.

M8 task 4 exposes loading through a busy results region and retains minimum height for list/detail states. Empty states and completed page counts use status semantics, without claiming a catalog total or moving focus away from search input. Explicit retry refocuses the page heading so removing the retry button does not leave keyboard focus on the document body. A failed replacement load hides older product data. Missing/retired products remain distinct from malformed responses, network/server failures and image failures; public 401/403 responses never trigger session renewal or a login redirect.

Use one catalog failure component for explicit list/detail retry. Honor valid integer Retry-After metadata with the same one-day advisory cap as auth forms, explain the disabled action and clear its timer on unmount. Elapsed time only enables the action; it never starts a request. The existing ten-second read deadline and late-response cancellation remain unchanged. This provides predictable recovery without adding a retry loop, exposing raw server diagnostics or changing backend policy.

M8 acceptance enlarges catalog links to a minimum 44px height and makes the skip link focus main directly, matching the existing error-summary link pattern. It preserves the current URL/history and loaded product links instead of creating a hash navigation and another read.

Remember at most 50 public catalog history-key/scroll-position pairs in the shell's in-memory outlet context. On POP, restore after results render so the shorter loading view cannot discard the position; wheel/touch/pointer/keyboard input cancels a pending restoration. Remove listeners when leaving the catalog. No product/private data, credentials or browser storage is involved; reload discards this memory and normal document behavior applies. New navigation still uses heading focus/top scrolling. This fixes the observed history regression without changing the selected router mode or adding a scroll/state library.

## 3. Authentication and privacy

Keep access tokens in memory; never store them in localStorage/sessionStorage or URLs. Refresh uses the existing HttpOnly cookie with credentialed requests and the required Origin/CSRF behavior. Restore sessions after reload, coordinate overlapping refresh attempts, bound retries, and test stale/concurrent browser behavior before accepting auth work. Frontend role guards do not replace server authorization.

Registration returns a user, not an access token. A deliberate login follows signup. Logout must invoke the server session endpoint and clear private client state; explain failures truthfully rather than promising revocation if the request did not complete. Do not log passwords, tokens, full shipping data or request bodies.

**Reason:** These choices preserve the existing session/cookie security design and avoid misleading browser authentication state.

Task 3 publishes a confirmed in-memory user/token only after login and `GET /users/me` both succeed. Its conservative display expiry starts at the login request, so latency cannot extend the token lifetime. A profile failure retains the accepted token only for an explicit profile-read retry; definitive 401 discards it. Registration never publishes identity or calls login. Read actual native form values on submission for autofill, count Unicode code points/UTF-8 bounds, and never trim/normalize passwords. Clear passwords after requests; retain nonsecret input, focus errors and guard duplicate submissions synchronously. Retry-After is an advisory UI wait capped at one day; the server remains authoritative and no request retries automatically.

Return paths allow home (validated q/offset), `/products/:productId` with UUID syntax, `/account` and `/admin`; product/private destinations accept no query/fragment payloads. Extend the allowlist only as destinations become functional. Already-confirmed users leave auth forms through replace navigation. M7 task 4 supplies the session lifecycle below; task 5 adds the private route/state boundary without claiming later feature caches are implemented.

The session controller owns credentials, conservative deadlines, profile confirmation and observable identity revisions; React subscribes to its public snapshot. Reload restores through the HttpOnly cookie. A per-tab flight coalesces refresh, while a native Web Lock serializes login/refresh/logout across same-origin tabs sharing that cookie. BroadcastChannel carries a small allowlist of state notices only, never tokens, profiles or passwords. Both APIs are required in a secure context (including localhost); unsupported coordination fails closed rather than introducing token storage or an unsafe independent refresh fallback. This uses the existing browser platform without another dependency.

Protected operations use `controller.authorized`: after a definitive HTTP 401, refresh/profile confirmation permits at most one replay for the same identity/role. Other HTTP failures, lost responses and protocol/network errors never replay mutations. Revision changes abort private requests and reject late results even if transport cancellation is ignored. Timers start at the credential request, and foreground/request checks cover suspended background timers. Expiry attempts one renewal; missing/rejected cookies become anonymous, while temporary/ambiguous refresh failures hide identity with explicit recovery and no retry loop. A retained profile candidate can retry the read alone while valid; expired candidates require fresh credentials.

Cookie operations, including lock waits, have a 20-second deadline. A lost committed rotation can make the old cookie unusable; deliberate sign-in is the recovery when the new secret was lost. Logout hides identity and broadcasts intent immediately, then waits for already-running rotations before revoking the latest shared cookie without requiring a JWT. Unconfirmed logout stays hidden, blocks automatic restore and offers explicit logout retry; it never promises server revocation. Peer notices also have bounded recovery if the initiating tab disappears. React StrictMode effect reattachment preserves the in-flight operation; actual unmount disposes resources after that immediate reattachment window. Server fixed session expiry/current-role enforcement remain authoritative.

Task 5's `SessionBoundary` waits for restoration, then checks the current profile on each protected navigation with a 20-second deadline. It preserves safe login return paths, hides private content during failed checks and offers explicit read retry. `AdminBoundary` checks that confirmed server role and gives customers a forbidden page. Guards improve navigation; the API still enforces every request. The new account view and admin landing make the boundaries usable now; account editing and product administration stay in M9/M11, including the eventual admin-products redirect.

Private features use `usePrivateSession` beneath the verified, revision-keyed subtree. Its request function pins the creating revision, uses bounded session authorization, cancels requests on navigation/unmount and rejects callbacks retained after their page or identity expires. Identity/role changes destroy local drafts/results and future caches under that subtree; successful same-identity renewal preserves them. M9 task 9 adds a shared cart controller pinned to this same revision; protected-page drafts remain beneath the boundary. No state library is added. Route-check effects ignore cancelled/older results, including StrictMode reattachment; feature caches introduced later must respect this identity lifetime. This provides explicit ownership and prevents old user intent from being submitted with new credentials.

Real browser tests reuse the fixture CLI, installed Go/goose and PostgreSQL. Each auth/session test builds native binaries, creates a fresh marker-owned database, starts its own loopback API on strict port 18080, and stops/removes only those resources. Per-test isolation prevents limiter/session state in one case from changing another case. Vite uses a test-only public API URL; root/development settings are unchanged. Public navigation checks stub only missing-cookie refresh and do not claim backend integration. A privacy reporter emits test names/source locations, numeric HTTP statuses and cleanup IDs, suppressing raw errors/DOM/worker logs; browser artifacts are disabled or not retained. This protects credentials while leaving failure locations inspectable, without adding a service, dependency or production test endpoint.

Final auth acceptance uses an integration-only Go test binary for four allowlisted fixture operations (expiry read/change, deactivation and demotion), reusing existing marker/configuration checks. The harness uses the private fixture key in its Node process to construct an actually expired signed JWT; the real API rejects it and performs normal refresh/replay. This proves server policy without changing production clocks/routes, waiting seven days or adding dependencies. Browser checks separately verify local cookie/Origin/CSRF/CORS and that auth does not write storage, expose credentials to console/URLs or broadcast credentials. [The test plan](TEST_PLAN.md#milestone-7-acceptance) records exact scope and evidence; future private features still need their own isolation tests.

## 4. Mutations and checkout reliability

M9 task 5 shares one bounded owner-scoped security-status read across verification and email-change controls. Initiation/replacement/cancellation clear password inputs, pin identity and never replay after 401; an uncertain outcome blocks further mutation until an explicit status read. `/confirm-email-change` reuses route-bound volatile link capture and inline sign-in, with no token in URL/state/storage/broadcast after capture. The transport separately validates 202 pending and 200 credential-change bodies, rejecting ambiguous/status-mismatched responses. The first proof preserves identity; final confirmation clears private state across tabs and requires new-email login. Any potentially final uncertain response hides private state and discards intent rather than replaying it. Existing SMTP/fixture infrastructure is reused; test-only proposed mailboxes and admission/JWT clock advancement use owned private IPC, while database token expiry stays on real PostgreSQL time.

M9 task 4 implements explicit email enrollment through `/account/security` and minimal `/verify-email`. Capture and remove link fragments before auth/router initialization, and repeat that scrubbing for same-document email reopening; retain the proof only in a volatile store, discard on navigation/identity change/use and reset page state for a newly opened intent. Inline sign-in avoids token-bearing return URLs. Verification writes share the cookie lock/deadline but bypass generic 401 replay; lost confirmation requires explicit profile reconciliation. Successful verification publishes `email_verified` without revoking sessions. Native integration-only TLS SMTP peers/private IPC prove browser journeys without production debug routes or external test mail. Actual TLS SMTP delivery and human mailbox receipt separately satisfy the task 4 gate; [evidence](TEST_PLAN.md#milestone-9-email-verification-progress) owns exact passing scope.

M9 task 3 implements `/account/security` through `SessionController.changePasswordFor`, outside generic authorized/replay handling. The existing same-origin lock serializes it with refresh/login/logout; page/revision guards block duplicate/stale intent, and the cookie deadline bounds even a noncooperative transport. Confirmed success clears identity/private state and broadcasts signed-out; a definitive form rejection retains the session, 401 never refreshes/replays the write, and an unconfirmed outcome hides private state with deliberate sign-in/session-read recovery. Password inputs clear when submission begins; confirmation is never sent. Cookie inclusion and CSRF metadata are distinct, allowing later public token calls without cookies. [Password evidence](TEST_PLAN.md#milestone-9-password-change-progress) records the task 3 scope; task 4 now adds SMTP/verified-email notifications.

Scope amendment (2026-10-25): M9 tasks 2–6 add authenticated password changes, email delivery/verification, verified email changes and emailed password resets. The profile form and PATCH remain name-only; dedicated password/verification/email-change flows are implemented and recovery remains task 6. The [shared scope amendment](../IMPLEMENTATION_DECISIONS.md#milestone-51-scope-baseline) and [ten-step plan](IMPLEMENTATION_SEQUENCE.md#milestone-9--account-addresses-and-cart) supersede the former recovery exclusion; they do not extend the current API by themselves.

Task 2 is complete: the [account-security design](../backend/ACCOUNT_SECURITY_DESIGN.md) is the single authority for selected contracts, migrations, lock ordering, token/session/legacy-enrollment policies, SMTP configuration and implementation/test gates. The browser uses dedicated security forms, volatile fragment tokens and send-once credential operations coordinated by the existing session lock. Password/reset/final email change revoke every session; current-email verification does not. Unverified legacy emails remain untrusted until mailbox proof. Delivery is best-effort after commit; SMTP acceptance is distinct from inbox receipt. No new infrastructure/provider SDK or current API/runtime behavior is introduced by selecting the design. Tasks 3–4 are implemented, and actual delivery/receipt is confirmed before tasks 5–6.

M9 profile editing lives in the account feature and uses only the existing GET/PATCH `/users/me` contract. Names use Go-compatible Unicode whitespace trimming and 1–200-code-point/NUL/surrogate validation. Compare normalized submitted values against the form's loaded baseline and send only changed first/last names; email/role stay read-only. No-change submissions perform no write. This avoids overwriting another writer's changes to an omitted field; the backend has no profile version, so concurrent edits to the same name still use last-write-wins semantics.

Revision-bound private helpers own profile reads/writes and reconcile validated server responses into the existing session controller. Same-identity/name updates preserve drafts and the revision; role changes retain existing private-subtree invalidation. Reject mismatched user IDs instead of publishing an unexpected account. The page replaces its form baseline from the full response and the header updates from that same server result, with no extra post-save GET or separate global profile cache. Other tabs get current names through their existing profile/session reads; no profile payload is broadcast or persisted.

Guard concurrent submissions synchronously and bound feature reads/writes to 20 seconds. A validation rejection keeps editable drafts; a lost, malformed, timed-out or otherwise unconfirmed save disables further saving until an explicit GET reconciles server state. Reload profile clearly replaces unsaved edits; a failed read retains drafts and does not unlock an uncertain write. Navigation/logout cancel requests, clear timers and reject late responses. The existing single replay after a definitive 401 remains the only automatic mutation replay. This makes uncertain outcomes reviewable without assuming rollback or adding mutation idempotency/schema changes.

Do not blindly retry ambiguous cart/account/admin writes. Refresh/replay behavior must distinguish a definitive authentication rejection from transport failure after a potentially committed mutation. Cart POST adds quantity and PATCH replaces it; successful mutations increment the server version. POST/PATCH return the updated cart, while DELETE returns 204 and needs a fresh cart read for the new version/state.

Checkout retains the original key, cart version, selected address ID and scenario for retries. A 503 or lost response does not justify a new key. M10 task 1 selects the [user-scoped persistence/recovery design](CHECKOUT_RECOVERY_DESIGN.md); implementation and acceptance remain tasks 2–9. A changed intent is a deliberate new submission after safe resolution and fresh review, not an automatic recovery tactic.

Map server terminal/pending/uncertain results to explicit UI states. Order/payment GETs only observe status, with bounded polling/backoff where appropriate. Customer UI never starts the operator recovery CLI, force-releases holds, or labels a timeout as payment rejection. Cancellation follows the same server restrictions/uncertainty policy.

**Reason:** Browser retries must preserve the backend's one-order and exactly-once inventory guarantees.

## 12. Checkout retry/recovery — Milestone 10 task 1

The [recovery design](CHECKOUT_RECOVERY_DESIGN.md) is the single authority for schema/validation, phases, lock names/order/budgets, durable handoff, error classification and cleanup. Select one minimal localStorage record per verified user/API base, persisted before any checkout POST. Original key/body remain immutable and unresolved metadata survives logout/reload/browser restart without age expiry. This is a narrow persistence exception for checkout metadata; credentials, full addresses, cart contents and speculative results remain excluded.

Require Web Locks and BroadcastChannel. Every record operation rereads under the per-user lock; use a five-second acquisition budget and no nested authentication locks.
