The [frontend sequence](IMPLEMENTATION_SEQUENCE.md#dependencies-and-acceptance-ownership) assigns implementation owners; the [integration inventory](API_INTEGRATION.md) records current backend support, screen/action/test requirements and gaps reviewed in Milestone 5.4. M13 Task 6 enables guest cart operations and explicit cart choice after sign-in. The guest checkout and order interfaces follow in Tasks 9–10, using direct contact and shipping fields and a server-recognized guest principal. Account/profile/address-book/admin access retains authenticated authorization. Administrators use intentionally provisioned accounts and server-enforced product/inventory permissions. Operators retain health, metrics, provisioning and recovery workflows outside customer screens.

|---|---|---|
| `FE-AUTH-01` | Signup | Valid registration creates a customer and empty persistent cart; duplicate/invalid input is explained. Signup does not imply login or allow a role selection. A deliberate login is available next. |
| `FE-AUTH-02` | Login | Valid credentials establish the current user/session and return the user to an appropriate page; invalid credentials, validation and throttling have clear feedback without exposing credentials. |
| `FE-AUTH-03` | Session restoration | Reload restores a valid session through the refresh cookie; overlapping refreshes are coordinated and retries bounded. Expired/revoked/inactive sessions return to signed-out UX and clear stale private data. |
| `FE-AUTH-04` | Logout/user changes | Logout invokes server revocation and removes private UI state. Failure does not claim successful revocation. Signing in as a different user cannot reveal the previous user's account/cart/orders. |
| `FE-CAT-01` | Public product previews | Guests and signed-in users see paginated active products with names, primary images/fallbacks, USD prices and availability. Loading, empty and API/image failures have usable states. |
| `FE-CAT-02` | Product details | A direct product URL shows its name, description, primary image/fallback, price and current availability. Missing/retired products are handled clearly; availability is a preview, not a reservation. Adding to cart is owned by `FE-CART-01`. |
| `FE-CAT-03` | Keyword search | Search performs literal, case-insensitive matching over active product names/SKUs across the catalog, with consistent pagination. An empty search returns normal browsing; no matches are explicit. Searching only the loaded page does not satisfy this criterion. |
| `FE-ACCOUNT-01` | Profile | A signed-in user reads/updates first/last names; omitted PATCH fields remain unchanged, null/invalid input is rejected clearly, and successful values survive reload. Credential changes are separate security flows below. |

| `FE-SEC-01` | Authenticated password change | Current-password verification precedes a valid replacement; incorrect/currently unauthorized attempts do not change credentials. The designed session-revocation/reauthentication policy is enforced, private UI state is cleared when required, and old/new credential behavior is tested. |
| `FE-SEC-02` | Email delivery and verification | Verification issuance/resend/confirmation and the configured delivery/failure path are tested. Expiring single-use verification proves mailbox control; existing accounts can acquire verified status without an automatic trust backfill. The designed signup/login/recovery eligibility policy is explicit. |
| `FE-SEC-03` | Verified email change | The current email remains authoritative until the replacement is verified through the designed confirmation flow. Duplicate addresses, reauthentication, expired/reused links, concurrent confirmation, notifications and session handling behave as designed without account takeover or ownership transfer. |
| `FE-SEC-04` | Forgotten-password recovery | Request/reset screens use non-disclosing request responses, abuse controls and expiring single-use emailed tokens for eligible verified addresses. Password replacement/token consumption is atomic, reuse/expiry is rejected, sessions follow the designed policy, and failures do not invent success. |
| `FE-CART-01` | Add to cart | A signed-in user adds a product/quantity; repeated intentional additions follow add semantics and update the quantity-sum badge from server state. M13 also permits guest additions/persistence without sign-in; no silent merge or automatic replay of an ambiguous add. |
| `FE-CART-02` | Edit/remove/clear | M13 uses a resulting-quantity dropdown (1–10 plus More… through 10000) with one replacement per deliberate selection and separate removal; Set/Add buttons are removed. Quantity replacement, item removal and clear persist with coherent versions after reload; empty, bounds/capacity/version and missing/foreign-item outcomes are handled. Bodyless responses are not parsed as JSON. |
| `FE-CART-03` | Cart presentation | Lines show product identity and supported price/image data with a clearly estimated subtotal. Missing/retired/unpriced lines remain explainable/removable; unknown prices are not fabricated as zero and partial totals are not represented as a complete subtotal. |
| `FE-CHECKOUT-01` | Review and submit | M13: a guest supplies contact/required US shipping, or a signed-in user selects/creates owned shipping; both review only the current cart and explicitly choose simulated acceptance/rejection. One submission retains one key and original version/address/scenario intent; repeat clicks cannot create replacement checkouts. |
| `FE-CHECKOUT-02` | Terminal checkout | New Project 1 payment attempts simulate acceptance. Historical failed/cancelled orders stay truthful; genuine business rejection and unknown/pending outcomes are never forced to success. Render the returned state, including a concurrent cancellation, rather than interpreting 201 alone as payment success. |
| `FE-CHECKOUT-03` | Interrupted/uncertain checkout | 202 shows a known pending order; 503/lost responses preserve original retry intent without claiming rollback or generating another key. Reload/navigation/user-switch handling is defined and tested before release. Status reads do not start recovery or infer rejection from expiry. |
| `FE-CHECKOUT-04` | Conflict resolution | Stale cart, insufficient stock, unavailable product, missing address and changed-intent conflicts produce specific guidance. Refreshing data or starting a genuinely new checkout is deliberate; resolving an uncertain submission keeps its original key/body. |
| `FE-ORDER-01` | Order history | A user sees only owned orders in stable descending creation/ID order with pagination, direct detail navigation and useful empty/error states. Changing users clears prior history. |
| `FE-ORDER-02` | Order/payment detail | A direct owned order URL shows immutable shipping/items/prices and current safe payment status. Foreign/missing IDs return an appropriate missing view. Pending observation is bounded and source catalog/address edits do not rewrite displayed purchase history. |
| `FE-ORDER-03` | Cancellation | Cancellation is available only before processing is claimed; repeat cancellation uses the same order and no body. 409 explains the current restriction; 503 preserves uncertainty and retries that same cancellation without promising rollback or refunds. |
| `FE-ADMIN-01` | Administrator access | Only a currently authorized administrator can use product/stock administration, including direct route/API attempts. Customer UI cannot grant roles; current server authorization wins over cached browser state. |
| `FE-ADMIN-02` | Product create/edit | An administrator creates/edits supported product fields, sees validation/SKU conflicts and preserves omitted fields. A new product starts with zero stock and can then receive an explicit stock adjustment. |
| `FE-ADMIN-03` | Retirement/reactivation | An administrator can find, inspect, retire and reactivate products after reload, including retired products. Retirement removes public availability without deleting purchase history; unsupported public reads are not used to fake an admin listing. |
| `FE-ADMIN-04` | Inventory | An administrator reads on-hand/reserved/available quantities and applies signed stock deltas. Bounds and reservation-floor conflicts are explained; browser controls cannot rewrite reservations or bypass server checks. |
| `FE-UX-01` | Responsive/accessible interaction | Critical journeys work at narrow (360 CSS px) and wide (1280 CSS px) layouts, with keyboard-reachable actions, labelled inputs, visible focus, readable contrast and deliberate focus/error feedback. Record tested browsers and limitations; no formal accessibility certification is implied. |
| `FE-UX-02` | Navigation and failure states | Direct page URLs, reload and back/forward work. Each feature has loading/empty/validation/conflict/network/server states, handles 204 correctly and bounds refresh/poll/retry behavior without silently duplicating mutations. |
| `FE-UX-03` | Contract, privacy and integration | All current business operations have an owned screen/action/test or documented exception. Component checks and real Go/PostgreSQL browser flows pass, including ownership/role denial; tokens/passwords stay out of persistent browser storage, and logs omit credentials and full profile/shipping payloads. |

The visual direction includes familiar header/account/cart navigation, product grids, a detail-page purchase panel, an editable cart summary and a clear checkout flow. Use keyboard-accessible controls, labelled forms, visible focus, readable contrast and layouts usable on narrow and wide screens. Loading, empty, validation, unavailable, conflict, expired-session and server/network-error states are part of each feature, not final cosmetic work.

Required page families are storefront/products, signup/login, account/addresses, cart, checkout, orders and admin/products. ## Scope boundaries

Prices, availability previews and cart estimates are not final checkout guarantees. The backend derives snapshots/totals and checks stock; the browser explains resulting conflicts. Order pages display retained order snapshots after source products/addresses change.

Payments are simulated. Do not collect real card data, imply a real charge, invent delivery guarantees, ratings, discounts or reviews, or show controls for unsupported operations. Reviews/ratings, Prime, recommendations, wishlists, marketplace sellers, coupons, taxes/rate calculation, refunds and complex fulfillment are outside the current baseline. Guest carts/checkout are approved M13 scope; silent merging remains deferred. Social login, customer role/account-activation administration, image uploads/galleries, shipping tracking, category/faceted filters and custom/relevance sorting are also deferred; the current scope needs one primary image, keyword search and the established catalog ordering. Adding them requires an explicit scope/contract increment.

Password changes, email verification/change and emailed password resets are now approved M9 scope (2026-10-25), superseding their earlier exclusion. They require new backend/API/schema/configuration work; the existing name-only profile PATCH does not implement them. M9 task 2 completed the [security/delivery design](../backend/ACCOUNT_SECURITY_DESIGN.md), including verification of existing accounts and provider-neutral SMTP. Queues/provider SDKs are excluded; password change is implemented with migration 10 and a dedicated security API. Tasks 4–6 implement token/verification/SMTP/email-change/reset flows; [combined M9 acceptance](TEST_PLAN.md#milestone-9-acceptance) is complete.

Health/metrics remain operational endpoints. Recovery stays a documented operator CLI, with status observation in the customer UI; there is no browser recovery/force-cancel action.
