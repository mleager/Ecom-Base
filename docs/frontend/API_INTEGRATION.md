## Browser session and HTTP rules

- Use direct CORS for the initial local setup: browser frontend `http://localhost:5173`, API `http://localhost:8080/api/v1`, exact frontend-origin allowlist, and credentialed auth requests. M7 verifies positive/negative auth, cookies and protected navigation against an owned API on localhost:18080. Do not mix `localhost` and `127.0.0.1` across normal browser URLs; security tests deliberately verify rejection. Alternate loopback settings must change consistently on both sides. SameSite=Strict cookies require compatible site settings; CORS alone does not fix cross-site cookies. No development proxy is needed for this baseline.
- Keep access tokens in memory and send bearer authorization on protected calls. Cookie-based login/refresh/logout require credentials and `X-CSRF-Protection: 1`; the browser supplies Origin, which must match the backend allowlist.
- The session controller coordinates cookie operations through Web Locks, broadcasts state notices only through BroadcastChannel and confirms the profile before publishing identity. Private features use `usePrivateSession().request` inside `SessionBoundary`: scope work to the creating page/identity, coalesce refresh and replay at most once after definitive 401 for the same identity/role. Protected entry checks the current profile before rendering; failures hide private content with explicit retry. Both browser APIs require a secure context; missing support fails closed. Browser guards cannot grant an administrator role; the API independently enforces it.
- Public calls include catalog/register/login and password-reset request/redemption; reset calls require the configured Origin/CSRF header and omit cookies/bearer credentials. Refresh uses its cookie, and logout uses an optional refresh cookie without requiring a live access JWT. Login/refresh/logout require exact Origin/CSRF. Remaining business calls require a bearer; administrator calls also require the current server role. Only definitive 401 permits the existing bounded same-identity renewal path for reads and name-only profile PATCH. Commerce, checkout, administrator and security writes use send-once paths without authentication replay, including after 401. Network/500/503 failures never establish rollback or justify silently repeating a mutation.
- Handle empty 204 bodies explicitly. Do not pass every response through unconditional JSON decoding.
- Preserve typed server `{code,message}` failures. Associate 400/422 input errors with forms, protected-call 401 with session handling, 403 with role/origin policy, 404 with missing/not-owned data, and 409 with deliberate conflict resolution. Public catalog 401/403 remain display failures without session renewal. Handle 413/429/500/503 truthfully; use Retry-After where returned and avoid retry storms.
- Use integer cents and documented JavaScript-safe version bounds. Formatting money is presentation; checkout totals and stock are authoritative only on the server.
- PATCH omits unchanged fields; null/unknown fields are rejected. Empty strings clear documented optional text. Current lists are arrays; product/order lists support `limit` 1–100 (default 20), nonnegative `offset`, and no total count. Addresses are an unpaginated owned list. Preserve query/page state without inventing page counts; a full page can offer Next, which may lead to an empty page. Only product lists gain search; orders retain the current strict limit/offset grammar.
- Profile PATCH edits first/last names only; email/role are read-only through this API. Product creation starts active with zero stock; retirement/reactivation and signed inventory adjustment are separate administrator actions.
- `Product.available_quantity` differs from `Inventory.quantity_available`; the latter also exposes on-hand/reserved quantities. Cart lines currently contain only item ID, product ID and quantity; mutations identify a cart **item** by its ID. The contract marks `Order.payment` optional even though the implementation supplies it: handle absence and read the safe payments endpoint when needed. Optional text/image fields need empty/missing fallbacks; order views use snapshots without rejoining catalog/address data.

## Checkout and cancellation outcomes

| Result | Required UI behavior |
|---|---|
| Checkout 201 | Show the returned terminal state, including simulated rejection or a concurrent eligible cancellation; 201 alone does not mean payment success |
| Checkout 200 | Show the retained order/current state; do not simulate again or invent a new intent |
| Checkout 202 | Show a known committed pending order and bounded observation; recovery remains an operator action |
| Checkout 500/503 / ambiguous or invalid response | Preserve the identical key/body; explicit Resume Original Checkout submits or resolves it. Absence of an order ID is not proof of rollback |
| Checkout 409 | Use the exact code/source-backed rejection table; `idempotency_conflict` preserves/blocks. Only a verified pre-commit refusal permits deliberate retirement and new review |
| Checkout 401/403 / generic validation | Preserve the intent; suspend for auth/access as needed, with no automatic write replay. An early refusal does not resolve a previous uncertain attempt |
| Cancellation 200 | Show the returned cancelled order, including repeat cancellation |
| Cancellation 409 | Refresh/explain current state; processing/terminal restrictions remain enforced |
| Cancellation 503 / lost or invalid response | Report uncertainty, observe current order state and offer only an explicit same-order cancellation retry; failed/still-pending reads do not prove rollback |

M10 implements the [retry/recovery design](CHECKOUT_RECOVERY_DESIGN.md) and passes [combined acceptance](TEST_PLAN.md#milestone-10-acceptance). Retain one minimal user/API-scoped localStorage record, save before send, and preserve immutable original key/body through navigation/reload/logout. Required per-user Web Locks/BroadcastChannel serialize cooperating tabs; every operation rereads under the lock. A validated order becomes a durable `known_order` locator before observations, followed by a post-handoff shared-cart refresh and deliberate new review. Corrupt/unsupported/unavailable storage preserves/blocks. No key/body metadata is broadcast, and no credentials/full address/cart contents are stored. The design owns exact validation, rejection allowlist, cleanup and request/polling budgets; production callers enforce coordination/identity guards and authoritative HTTP evidence before transitions.

Verified integration behavior: the client accepts checkout 200/201/202 with the captured custom key; generic `authorizedFor` may replay a 401 and is not used for checkout. Submission uses the send-once identity-pinned write path. CORS allows `Idempotency-Key`; checkout uses bearer authentication without cookies/CSRF. OpenAPI permits absent `Order.payment` despite Go supplying it, so retain a valid order ID and use the existing payments GET without inventing a payment result. The implemented post-handoff cart barrier requires a fresh read generation before replacement checkout. No backend behavior or endpoint change is selected. Payment selection remains explicitly a lab simulation, with no card form/provider.

## Bounded cart presentation

1. Read the owned cart and its version; deduplicate its at most 100 product IDs. Fetch current public product details with at most four concurrent requests, one attempt per product per cart-load generation and a ten-second overall enrichment deadline. At the deadline, abort remaining requests and mark unresolved/unstarted lines as unpriced with explicit retry feedback. Cancel/ignore stale results after navigation, a newer cart load or identity change; explicitly retry failed enrichment rather than looping automatically.
2. Active products supply name/SKU/image/current price/availability. A 404 means unavailable, without claiming whether missing or retired: show the product ID, quantity and removal action, with an unavailable label/image fallback. Network/500 failures remain distinct retryable display errors. Removing/clearing always uses cart item IDs/current cart state independently of enrichment.
3. Show an estimated subtotal only when every line is priced and checked multiplication/sum stays within the backend's 1,000,000,000,000-cent line/order bound. Check before arithmetic so large allowed price/quantity combinations never create an unsafe JavaScript number. Otherwise explain incomplete/out-of-range estimates; never substitute zero or label a partial sum complete. Checkout always recalculates authoritative totals.

This needs no new endpoint and preserves active-only public reads. The tradeoff is up to 100 bounded product requests; M6 verifies the data/fallback assumptions and records the [test boundaries](TEST_PLAN.md#cart-data-and-arithmetic-readiness). M9 task 8 implements the scheduler and [proves](TEST_PLAN.md#milestone-9-cart-progress) the 100-product/four-request bound in deterministic tests, plus slow/failing reads, identity/navigation cancellation and visible fallback/removal in real browser journeys. An enriched/bulk API is not part of the selected scope and would require a later justified contract change.

Task 8 connects all five bearer-only operations at `/cart`. Runtime guards reject malformed/duplicate/oversized lines or unsafe versions. POST/PATCH apply the returned complete snapshot/version; DELETE 204 is followed by GET rather than local version invention. Older/different-cart snapshots fail closed. Quantity edits/removal do not wait for product enrichment, though known unavailable products cannot accept quantity changes. Inline clear confirmation, empty/reload states and current USD estimates are implemented; a complete subtotal requires every price and safe arithmetic.

Reads/writes have twenty-second deadlines. Writes send once through the existing identity-pinned session path, without 401 renewal/replay. An unconfirmed write blocks edits until an explicit successful GET; a definitive 204 is reported separately from failed readback. Explicit reload replaces unsaved quantity inputs and restores otherwise-lost keyboard focus. Automatic observations keep current rows while checking and preserve drafts/enrichment for unchanged coherent versions; contradictory same-version lines fail closed. A changed server quantity reconciles its input. Prices remain observations from the last detail load, refreshed through explicit Retry product details. Task 9 shares a cart controller across same-identity routes: a submitted write can finish through SPA navigation, while drafts/enrichment end with their pages. Identity/session-revision changes abort private work, clear the snapshot and ignore old results. No full cart/drafts enter browser storage/history. [M9 acceptance](TEST_PLAN.md#milestone-9-acceptance) records combined scope and limits.

The header badge sums server quantities across lines; pending/failed/uncertain observations show updating/unknown rather than zero. Purchase controls and the badge do not enrich products. Route entry and foreground checks coalesce owned GETs; a separate best-effort browser channel emits only `changed`, prompting receivers to read their own state. Notices during successful observations/confirmed writes retain a follow-up read; a definite write rejection also observes a queued peer change. Automatic observations never clear an uncertainty block, and failed reads never loop. Minimal email/recovery pages start no cart/product reads. [Storefront integration evidence](TEST_PLAN.md#milestone-9-storefront-integration-progress) distinguishes these behaviors from final combined acceptance.
