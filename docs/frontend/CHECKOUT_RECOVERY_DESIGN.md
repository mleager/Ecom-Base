## Verified contract and architecture

M13 [guest recovery design](../backend/GUEST_COMMERCE_DESIGN.md#browser-persistence-and-coordination) selects a separate guest v2 slot with an immutable server-prepared shipping reference, while preserving these implemented user v1 records/bytes. Guest preparation, scoped mailbox access, expiry/retirement fences and tagged-owner/cart-choice lock ordering are planned extensions, not behavior already supplied by this controller or GAP-06 acceptance.

- [`CreatePending`/`create`/`lookup`](../../backend/internal/checkout/service.go) validate syntax/actor, look up the retained user/key, then acquire a transaction advisory key lock and repeat the lookup before consulting mutable cart/address/stock. T1 atomically creates the order/intent/snapshots/reservations and consumes/increments the cart. A matching key returns the retained order even after cart/address/product changes; a different intent conflicts.
- [`Checkout`](../../backend/internal/checkout/orders.go) processes only an acknowledged new T1. Replay is observation only. A rollback can leave no order; lost COMMIT acknowledgement, post-T1 integrity failure or lost HTTP reply can leave a committed order. Neither a 500 nor an absent history entry proves rollback. Only operators run reconciliation; expiry never authorizes browser stock release.
- [`http.go`](../../backend/internal/checkout/http.go) maps new terminal/pending/replay to 201/202/200. Order/payment pairs are `pending_payment` with `pending|processing`, `confirmed/succeeded`, `payment_failed/failed`, and `cancelled/cancelled`. A 201 may contain payment rejection or a concurrent cancellation. Cancellation is bodyless, owner-only, and available only before a processing claim; repeated completed cancellation is 200.
- [`SessionController`](../../frontend/src/features/auth/session.ts) exposes verified identity/revision, aborts obsolete private requests, coordinates cookie operations, and distinguishes `authorizedFor` (one possible 401 replay) from `writeFor` (send once). [`SessionBoundary`](../../frontend/src/features/auth/SessionBoundary.tsx) verifies protected route entry and owns page cancellation. Checkout must use the send-once path, never the generic replay path.
- [`CartProvider`](../../frontend/src/features/cart/CartProvider.tsx)/[`CartController`](../../frontend/src/features/cart/CartController.ts) share one volatile snapshot per identity/revision above routes. Checkout recovery is a separate minimal persistent store, not a saved cart or an extension of cart drafts. Checkout review/order pages remain protected; no metadata is restored while identity is unknown.

Contract differences and implementation work from the Task 1 inspection baseline, without changing the backend. Task 5 now implements the selected transport/cart treatment:

| Finding | Selected treatment / owner |
|---|---|
| OpenAPI `Order.payment` is optional; Go `loadOrder` supplies it | Accept a valid order without payment, retain its ID, show payment unavailable and use the existing payments GET. Never infer payment success from order HTTP status. Invalid present payment makes the response invalid. Tasks 5/7. |
| Current frontend operation metadata supports one success status plus an optional pending status, and its client has no checkout/custom-key operation | Add a checkout-specific typed 200/201/202 response boundary and `Idempotency-Key` support in task 5. Existing CORS already permits that header; bearer-only checkout omits cookies/CSRF. |
| Current cart `invalidate` can coalesce with a read started before checkout; it is not a checkout refresh barrier | Task 5 must invalidate the old read generation/snapshot and obtain a post-handoff cart read. Block new checkout until that read succeeds and the customer reviews it. |
| Server auth/checkout contexts are five seconds, fresh commit resolution is separately bounded, HTTP write timeout is fifteen seconds | Keep the approved client POST deadline at thirty seconds and GET at ten seconds. They are client ceilings, not extensions of server execution or proof of rollback. |
| Error responses share schemas; generic `invalid_input` can arise both before lookup and inside T1 | Use the source-backed allowlist below, never all 4xx responses. No backend validation or transaction change is selected. |

## Persistent record

Use exactly one slot per verified canonical user ID and configured API base. Storage key and exclusive Web Lock name are both `commerce-lab:checkout:${encodeURIComponent(configuredApiBaseUrl())}:${userId}` (separate browser namespaces). Keep this name stable across record schema versions so an unsupported version cannot be bypassed by creating another slot. Do not enumerate/read other users' slots. The record is canonical JSON, schema version 1:

| Field | Exact validation |
|---|---|
| `schema_version` | Integer `1` only. |
| `user_id` | Lowercase hyphenated UUID, exactly the verified user/slot. |
| `idempotency_key` | Lowercase RFC 4122 version-4 UUID, exactly 36 characters, generated once with `crypto.randomUUID()`. This is a deliberate subset of the backend's 1–128 visible-ASCII key contract. |
| `request` | Object with exactly `cart_version`, `shipping_address_id`, `payment_scenario`, serialized in that order. Version is a safe integer 1–9007199254740991; address is a lowercase hyphenated UUID; scenario is exactly `accept` or `reject`. |
| `created_at` | Canonical 24-character UTC ISO timestamp (`YYYY-MM-DDTHH:mm:ss.sssZ`), valid and round-tripping through Date. Informational only; no age cutoff or expiry. |
| `phase` | Exactly `unresolved`, `known_order`, or `rejected`. |
| `generation` | Independent lowercase version-4 UUID generated for each new deliberate intent; never reused. |
| `revision` | Safe integer 1–9007199254740991, initially 1; increment for each phase update. Exhaustion blocks updates rather than wrapping. |
| `order_id` | Required lowercase hyphenated UUID only in `known_order`; forbidden in the other phases. |

Use exactly the listed top-level fields in the listed order, with optional `order_id` last. Reject extra/missing fields, nulls, coercion, invalid nested shapes, unsupported versions, noncanonical encoding (including duplicate JSON keys), and raw values above 4096 UTF-8 bytes. Bound raw length before parsing, validate, then compare with the canonical reserialization. Do not normalize or rewrite invalid stored data. Never store credentials/tokens, full addresses, cart items, prices, order/payment results, error bodies or persistent session revisions. Capture a detached immutable request from a deliberate current review; the key, request, user, timestamp and generation never change in that record. Treat storage input as untrusted, even if previously written by this app.

`unresolved` covers saved-but-not-yet-sent, in-flight and uncertain submissions. A crash between persistence and transport deliberately restores the same conservative state: Resume may create the original order. `known_order` is the durable handoff/locator, not a cached payment result. `rejected` records only that a source-verified rejection established no committed order for this key; its explanatory error can remain volatile. These last two phases are resolved intents, not blockers forever.

## Coordination and lifetime

Web Locks **and** a functioning BroadcastChannel are mandatory for checkout writes, as for [authentication coordination](../../frontend/src/features/auth/coordination.ts). Fail closed if either cannot be established. Use one checkout channel per configured API base, `commerce-lab:checkout:${encodeURIComponent(configuredApiBaseUrl())}`, carrying only the literal `changed`. No record, key, user ID, generation, order ID or credentials enter messages. Also treat storage events, route entry and foreground return as invalidations; read only the current user's slot under its lock. Notifications never submit or restart polling, and cannot be used as record contents. Delivery failure blocks further checkout writes until coordination is re-established; it never changes an already committed server outcome.

All production recovery-record reads, validation, creation, phase updates, retirement/replacement and submission run through one exclusive per-user coordination boundary. Task 2 provides testable persistence primitives for use only inside that boundary; task 3 makes the boundary mandatory. Do not expose an uncoordinated production mutation path.

1. Finish any needed authentication restoration/profile verification **before** requesting the checkout lock. Pin the verified user, local session revision and page/action lifetime. Wait at most **five seconds** for this lock; cancel the queued acquisition on navigation, identity change or page inactivity. Busy/timeout offers a deliberate retry without a queued later submission.
2. Reread and strictly validate persistent state after acquisition, including when a notification prompted it. Recheck current authenticated identity/revision, page lifetime and access deadline. If auth needs renewal, release the checkout lock, handle auth separately and require another explicit submit/resume action. Never await auth restoration under this lock.
3. For a new intent, reread absent/resolved state, require fresh review, create/persist/read back the record, and send once. For Resume, reread the matching `unresolved` record and use its exact immutable key/body. Hold the lock through the bounded POST and any permitted result persistence/readback. Task 5 gives the granted operation a thirty-five-second ceiling (thirty-second POST plus bounded finalization), independent of the five-second acquisition budget. Persist before transport; if it fails or reads back unexpectedly, send nothing.
4. Release the lock before order GETs, cart refresh or any polling. Auth cookie paths never acquire the checkout lock; checkout paths never acquire/await the auth lock. `writeFor` performs a synchronous identity preflight/send-once operation and can reject; it must not renew. This no-nesting rule avoids lock-order cycles.

All callbacks compare expected user/key/generation/revision and immutable fields against a fresh locked read, not an old in-memory object. Updates use revision + 1; deletion/replacement requires the exact expected record. A mismatched/newer record is preserved and reread, never overwritten, deleted or resurrected. Unexpected disappearance/change during an active operation blocks that flow even if the new value looks valid. Local commands have a synchronous latch to prevent double-clicks; the mandatory lock serializes cooperating tabs. An event received while a lock is held queues/coalesces a later read, never a nested lock request.

Check monotonic elapsed time before transport/late auth continuations and before accepting results, as well as racing abort timers. Abort transport and race it against the deadline/lifetime so even a noncooperative Promise cannot retain the lock indefinitely or publish late. After cancellation, identity replacement or uncertain persistence, leave the last durable record untouched; abort is not server rollback. Another explicit same-key attempt is safe even if the old backend operation is still finishing because the backend key lock serializes it. Do not issue asynchronous cleanup that can outlive the lock. Synchronous localStorage calls cannot be preempted; keep payloads bounded and perform no unrelated work under the lock.

Place the recovery owner at the verified identity/revision lifetime, with page-bound commands and presentation under the existing private boundary. It retains no old private UI on logout/account replacement and cancels queued/active obsolete work. Stored unresolved metadata survives logout, browser restart and navigation; restore only after same-user verification. A stale response must not update storage merely because its original account's slot still exists. Minimal email/recovery pages do not expose checkout recovery or start checkout/order reads.

## Durable handoff, retirement and replacement

Accept an order ID only from a valid authenticated checkout response for the current request, with valid required Order fields/snapshots, bounded integer money/quantities, coherent totals and recognized statuses. If payment is present, validate its shape/status pairing; if absent, use the existing payment read later. 201 must be terminal, 202 pending, and 200 may be either. There is no user ID or source-cart intent in the response to compare: ownership/request association comes from the pinned bearer operation, not a guessed history match or a URL/storage-provided ID. Once an order ID is known it cannot be replaced by a different ID for the same intent.

Under the same lock, verify matching identity/record, replace `unresolved` with `known_order` plus the authoritative `order_id` and incremented revision, and read back the exact persisted value. **That one-slot phase transition is the durable handoff.** Do not remove the record to navigate, retain only a transient URL as the handoff, or wait for terminal payment before persisting. On failed/unknown persistence, preserve whatever is stored and block replacement; the original key/body remains the recovery path if `unresolved` is still present. If a later locked read confirms `known_order`, observe it instead of replaying. A successful HTTP reply alone never justifies retirement.

After handoff, release the lock, display/link the known order and use GET `/orders/{id}` and `/orders/{id}/payments`. Invalidate the shared cart and all reads begun before the handoff; get a fresh server snapshot, requiring a version greater than the original consumed `cart_version`. Hide obsolete totals/badge and block new checkout until refresh succeeds. Cart changes during observation require another review. A failed refresh does not remove the order locator. A known pending order can coexist with another deliberate purchase once its handoff is durable, cart refresh succeeds, and a new current review is explicitly submitted.

Keep `known_order` indefinitely until the next deliberate, freshly reviewed submission atomically replaces that exact record with a new persisted `unresolved` generation/key/body. Do not delete it first. Existing owned order history/detail remains the durable server source for the previous order, including pending orders; no growing browser order archive is added. Even terminal observation does not automatically erase the locator. Failed/404 order reads preserve it, never revert it to replay or infer rollback. Reloading `known_order` forces fresh cart review before replacement; no persisted "cart refreshed" flag is trusted.

For the definitive allowlist below, persist/read back `rejected` under the lock before enabling **Retire rejected checkout and review again**. This never happens for a generic validation/auth error. Production submission refuses direct replacement of a rejected record: explicit matching-record removal with verified absent readback must precede fresh cart/address/simulation review. Retirement creates no key and sends no checkout; a later deliberate placement creates the next intent. The general persistence primitive still supports atomic resolved-record replacement, but production uses it directly only for known orders. No automatic new key, automatic submission or age cleanup occurs. Failed/unknown removal blocks checkout and preserves whatever is stored for inspection. Transient fixed rejection guidance need not survive reload: a valid `rejected` phase explains definitive refusal without inventing its reason.

## Response and state transitions

The authoritative error envelope is bounded `code`/`message` JSON. Checkout requires `application/json`, at most 8192 raw UTF-16 code units, exactly two unique decoded property names (`code`, `message`) with code length 1–128 and message length 1–1024 UTF-16 code units, and the **matching HTTP status and exact code** below. Duplicate/extra fields, wrong MIME, malformed envelopes and unrelated API errors cannot establish retirement evidence. Never classify by HTTP status alone. A late response beyond the monotonic POST deadline preserves uncertainty even if its timer callback has not run.

| Current state / observation | Persistent transition and action |
|---|---|
| No record or deliberately replaceable known order; explicit reviewed submit | Persist/read back a new `unresolved` record, then one POST with its key/body. |
| `unresolved`; reload, foreground, peer notice or auth renewal | Locked read only; explain recovery and offer explicit Resume Original Checkout. No automatic POST. |
| `unresolved`; valid 201/200 order or valid pending 202 order | Persist/read back `known_order`, then observe returned authoritative state and refresh cart. HTTP success is not payment success. |
| `unresolved`; 500, 503 (including `checkout_outcome_uncertain`), timeout, lost/malformed/unexpected response | Preserve/block new intent; explicit same-key/body Resume can submit or resolve. |
| `unresolved`; 401 or generic 403 | Preserve; suspend controls and handle authentication/access outside checkout coordination. No 401 write replay. |
| `unresolved`; 409 `idempotency_conflict` | Preserve/block; explain intent inconsistency. Never edit the stored body or generate a replacement key. History/operator investigation is available. |
| `unresolved`; verified pre-commit allowlist below | Persist/read back `rejected`; offer explicit matching retirement, then fresh review. This is not an order/payment rejection. |
| `rejected`; explicit matching retirement | Remove/read back absence under the lock, then reread cart/addresses and clear choices. No POST/key until later deliberate reviewed placement. |
| `unresolved`; any other status/code, including generic validation | Preserve. This request's early refusal cannot resolve an earlier uncertain submission. |
| `known_order`; valid observation | Keep the locator; display current order/payment state. Pending observation never POSTs checkout. |
| `known_order`; unsuccessful/invalid GET or observation budget exhausted | Preserve; show unavailable/still pending with manual Check Status, never assumed failure. |
| Any state; storage/coordination failure, identity/lifetime change or stale callback | No destructive transition or late publication; hide obsolete private UI and retain durable state. |

The following errors are raised by `create` **after acquiring the key lock and finding no matching retained intent**, before T1 commit. Existing committed intent wins lookup first, so this barrier also resolves an earlier uncertain same-key attempt. Failed reservation increments roll back together. These facts justify this narrow allowlist; a future backend change must reverify it.

| Status / code | Verified cause / deliberate correction |
|---|---|
| 409 `stale_cart` | Requested cart version differs; reload/review current cart. |
| 409 `insufficient_inventory` | Conditional stock reservation fails; review quantities/availability. |
| 409 `product_unavailable` | An inactive product is present; remove/review it. |
| 404 `address_not_found` | Owned address lookup or address normalization fails; select/review a valid owned address without disclosing foreign existence. |
| 422 `empty_cart` | No lines after cart/version checks; return to shopping. |
| 409 `cart_version_exhausted` | Cart at 9007199254740991 cannot be consumed; seek operator help, never reset/decrement it in the browser. |
| 422 `invalid_checkout_total` | Checked line/order arithmetic exceeds the 1000000000000-cent bound; review quantities/products. |

Other implemented validation errors are **not** on that allowlist: 400 `invalid_idempotency_key`, `bad_request` (malformed UUID), `invalid_json` (including missing/extra/duplicate/null/wrong-type fields), 413 `body_too_large`, and 422 `invalid_input` (scenario/version, also an oversized cart internally). They can precede key lookup, so preserve an existing unresolved record even when the current attempt clearly did not run T1. 401 `unauthorized`, 403 origin/CORS policy errors, unknown codes and malformed error bodies likewise cannot resolve it. Do not offer unsafe record deletion as a recovery shortcut.

Cancellation is separate from checkout intent: POST the same known order, no body, through send-once transport and explicit confirmation. 200 must validate cancelled state; 409 `cancellation_conflict` prompts a current order read; 503 `order_outcome_uncertain`, 500/lost/invalid responses retain uncertainty. Only a validated terminal state establishes the current outcome; a failed read or still-pending state does not prove cancellation rolled back. Any cancellation retry is explicit for that same order, with no new checkout key, forced cancellation, refunds or expiry-based release.

## Request and observation budgets

- Checkout POST: **30 seconds**, starting at transport invocation, separate from the five-second lock wait. Cancellation POST retains Task 7's selected/implemented **20-second** feature-write ceiling. Task 8 corrects the former thirty-second cancellation wording; it changes no cancellation/server timeout. Use cancellation/deadline races and stale-generation checks, not only fetch abort. No automatic retry after timeout, 401 renewal, 500/503, navigation or restoration.
- Order-status GET: **10 seconds** per logical read, including any bounded auth renewal. Never let late auth completion send a resource read beyond its deadline. Missing-payment fallback uses the same deadline; do not overlap it with an order read.
- Automatic observation: one order GET immediately, then **3 seconds after the previous read completes**, one resource read in flight, at most **60 elapsed seconds or 20 actual order/payment GET attempts**, whichever comes first. A 401 resource replay or payment fallback counts as another attempt. Enforce the overall deadline during an in-flight read and before every transport; clip its budget to remaining time. Use monotonic elapsed time in the page, not the informational record timestamp.
- Stop on terminal order state, read/auth/protocol failure, budget exhaustion, navigation, identity change, hidden/inactive document or observing-page disposal. Cancel obsolete reads and ignore late results. Poll only the active order detail/observation page, never header/history/background tabs. Do not hold the checkout lock while reading status.
- Offer manual **Check Status** after stopping. It performs one bounded observation (and necessary payment fallback within its budget), not another automatic loop. Focus/visibility return, broadcasts, auth renewal and manual checks do not silently reset automatic budgets; a newly navigated/reloaded observing page may start its own bounded window. Pending/timeout is not payment failure. No GET or replay resumes payment processing, reconciliation or stock release.

## Failure presentation and limitations

Before Resume, explain: "Resume Original Checkout may find your existing order or submit the saved original request if no order committed. It uses the same key and request. If no order committed, current prices and address values still apply. It will not restart interrupted payment processing." Keep original version/address ID/scenario immutable even when current cart/address data changes. New checkout is blocked until resolution; Resume itself is deliberate, never an effect or a generic retry button.

Unreadable/unavailable localStorage, invalid/unsupported records or unexpected active-flow changes preserve the existing bytes and block new checkout. Provide an actionable message to restore browser storage/access, recheck explicitly, and open owned order history; do not silently delete, repair, migrate or overwrite. Successful reads must not clear a previously observed active-flow inconsistency without explicit review. Storage failure after server success does not mean the order failed.

Clearing browser data, a different browser/profile/device or external modification can remove recovery metadata; fresh startup cannot distinguish a genuinely absent record from cleared storage. History remains available, but exact submission identification cannot be guaranteed without the original key/body. Do not match orders by timestamp/total or synthesize a replacement intent from history. Application user scoping prevents cross-account display/submission; localStorage is **not confidential** from same-origin JavaScript or someone with browser-profile access. Web Locks coordinate cooperating tabs, not arbitrary scripts/devtools; preserve detected changes and document that external clearing/tampering is outside that guarantee. Browser storage is not a server backup or a guarantee against browser eviction. No unresolved record expires solely by age.
